# Elekta 二面：架构师面试备考路线

更新：2026-10-10。已知：一面基础知识已通过；二面是架构师面试，据用户了解可能有现场编程，以非算法任务为主。已确认现场可以使用Java；面试日期、时长及工具规则未确认。下面是备考练习，不是已核实的 Elekta 题库或内部架构。

## 1. 这轮要练什么

把重点从“解释一个名词”移到“给定需求，做出小而完整的设计，写出可检查的实现，再说明失败路径”。每题按以下顺序练：

1. 用英文确认需求与边界。
2. 给出一个具体正常例子和失败例子。
3. 画对象关系或调用流程，说明状态归谁管理。
4. 写最小实现，优先守住业务规则。
5. 跑测试，解释并发、失败与扩展的限制。

> Let me confirm the expected behavior first.
>
> I will start with a small working version.
>
> Then I will test the failure cases and explain the limits.

建议精力分配：现场编程 35%，项目深挖 25%，设计与测试 25%，行为题及英语 15%。这是准备策略，不是题目出现概率。

## 4. 当前材料的冲突与更新

最新简历写有 React、ASP.NET Core、MySQL、Python/FastAPI 的肿瘤研究平台。旧备考资料“没有 C#/.NET 项目”的口径已经不能直接套用。可区分：**企业工作主要是 Java；研究/个人项目有 .NET 实践；没有已证实的医疗商业生产或正式 QMS 经验。**

简历中的研究项目时间为 2022.03–2022.09，当前仓库文档同时区分历史项目和近期复现。面试前列清“历史实际完成 / 近期重新实现 / 后续设计”，不能把所有当前实现都自动归入 2022 年。

退款在简历中写“多锁竞争死锁”，旧资料进一步说明抢锁失败退出且锁有 TTL。最新完整方案补充：单条消息在消费者内组装完整退款组，完整排序后才拿第一锁；扫描重投与超时单退推进未完成记录。“当前退款置顶”是选定还原而非源码已取证。回答先讲相反锁序的交错，再解释不是永久阻塞；这比单纯争论用词更有说服力。

保险查询优化在最新简历中有量化主张，但旧资料表示实施与指标证据不足；PDF 部分数字存在文本提取缺字。准备时核对原始指标、分位数、采样环境和个人改动，不补猜数字。

招行简历的“首屏提升40%+”不能直接证明 API 服务端变快。旧资料提到 P95 FCP；用什么指标、如何计算、是否控制设备和缓存条件，需要本人确认。

## 5. 英文规则

主答案 4–7 句，一句表达一件事。技术词无法替代时保留，如 transaction、idempotency、version conflict，但紧接一个例子。不要用长句堆多层条件。

经历：I worked on / I changed / I learned。

解释：This means / For example / The key point is。

方案：I would / My first step would be。

不知道：I have not done that in production. Here is how I would approach it.
