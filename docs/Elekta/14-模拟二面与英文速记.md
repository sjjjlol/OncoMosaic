# 二面模拟、训练计划与面前速记

配套09–13。默认用简单英文；一面已通过，基础概念放在项目追问里练。面试实际时长和形式仍待确认。

## 1. 75分钟模拟二面

| 时间 | 面试官题目 | 应交付 |
|---|---|---|
| 0–4分钟 | Tell me about yourself. Why this role? | 60秒介绍+30秒动机 |
| 4–16分钟 | Tell me about a challenging project. | 退款交错图、个人改动、锁与幂等边界 |
| 16–25分钟 | Explain a technical point from your CV. | 肿瘤平台的一个完整链路或EasyAccess变化点 |
| 25–50分钟 | Implement a small versioned store. | 主路径、版本冲突、至少3个有价值测试 |
| 50–64分钟 | Design a booking system, including UML. | 假设、不变量、类图、创建时序、并发保证 |
| 64–71分钟 | Code review / failure / schedule / audit. | 每题4–6句；真实经历与假设分开 |
| 71–75分钟 | Your questions. | 团队模块、质量协作、前三个月期望 |

完整35分钟编程或完整30分钟设计可另单独练；75分钟模拟只是压缩训练，不代表实际面试安排。

评分每项0–2分：需求澄清、模型合理、正确实现、失败/并发、验证证据、英文易懂、事实边界。0=无法继续，1=需要提示，2=能独立解释。不能拿总分预测录用。

## 2. 三天训练，每天约3小时

### 第一天：故事与英文

- 30分钟核对11里的个人事实，列历史/近期/建议三列。
- 40分钟退款90秒录音；听后删除重复和长句。
- 40分钟按表练锁过期、超时、幂等、入口排序四个追问。
- 40分钟肿瘤平台与EasyAccess各讲一个机制。
- 30分钟用退款案例练失败与反思、技术核查两种说法；准备SDLC事实口径。

产物：自我介绍、退款故事和一个项目追问的录音；一页事实清单。

### 第二天：现场编程与测试

- 20分钟只看12的契约，口述测试矩阵。
- 35分钟用Java不看参考实现版本化store。
- 25分钟运行，解释一个失败和一个并发测试。
- 30分钟做12的代码评审题并改写。
- 30分钟练供应商规则重构或重复消息处理。
- 20分钟练GCD、virtual/new、稳定排序。
- 20分钟解释真实数据库与内存练习的差别。

产物：自己写的版本、测试结果、失败复盘。看过参考后能运行，不等于现场能独立完成。

### 第三天：设计与模拟

- 35分钟从空白画预约类图和创建时序。
- 25分钟回答“两个用户同时预约”“改期失败”“通知超时”。
- 75分钟做完整模拟并录音。
- 25分钟只改最弱两项。
- 20分钟口述最后速记与反问。

若只剩一天：退款45分钟、store60分钟、数据库测试30分钟、系统设计45分钟、行为英文30分钟、模拟45分钟。不要先读完所有医疗标准。

## 4. 现场英语：可以直接说的短句

| 场景 | 句子 |
|---|---|
| 确认需求 | Let me confirm what should happen in this case. |
| 要一个例子 | Could you give me one example of the expected result? |
| 确认编码语言 | I will use Java for this task. |
| 确认工具规则 | Are documentation and code completion allowed? |
| 想几秒 | Let me think through the state changes first. |
| 说明假设 | I will assume this is a single-process version for now. |
| 说明选择 | I chose this because the update needs to be atomic. |
| 下一步 | I will test a normal case and a conflict case next. |
| 发现错误 | This check leaves a race. I will move it into the atomic update. |
| 时间不足 | I will finish the main path and one failure test first. |
| 不知道语法 | I know the intended behavior, but I need to check the exact API name. |
| 没做过 | I have not implemented that in production. My approach would be… |
| 没听清 | Could you repeat the last part? |
| 避免猜 | I do not remember the exact number, so I do not want to guess. |
| 回到贡献 | My own change was the lock order at the entry point. |
| 总结限制 | This example does not test a real database transaction. |

不需要持续朗读每一行代码；每完成一个有意义的步骤说一句。

## 5. 常见“卡住”时怎么继续

**不会某个框架API：**说明需要的行为，先写小接口或纯函数，征得允许后查文档。别把不会语法误说成不会设计。

**需求变化：**复述新增规则，指出影响的状态/模型/测试，先改最核心处。例如允许Confirmed取消，需要改变合法转换和Slot释放，不能只删一个if。

**代码跑失败：**说实际与预期，定位最小失败，修复后重跑相关测试。不讲“应该能跑”当验证。

**不知道规模：**问并给明确小规模假设，先保证正确性。扩容问题另说明原子领取、索引和下游容量；不凭空报QPS。

**面试官挑战设计：**先判断是不是业务假设变化，再比较选项；说“I would change the design if…”比机械坚持模式更自然。

## 6. 面前10分钟速记

1. 退款：one message per record → consumer builds full group → sort full group → first lock；尚未完成扫描重投，尚未提交过时限才单退。
2. “当前＋其他”置顶是选定还原；不能先锁当前记录。抢锁失败return不等于MQ自动重试；TTL和排序不保证资金效果幂等。
3. 超时：unknown result；same request ID；query/reconcile before retry。
4. 编程：contract → state rules → atomic version update → tests。
5. 测试：正常、缺失、重复、边界、并发、回滚；检查最终数据。
6. 设计：不变量、类图、时序图、事务边界；可用性查询不是最终占位保证。
7. 简历：.NET研究/当前实践与Java企业经验分开；历史日期、指标口径不猜。
8. 导出：fixed review version；跨请求不是开一次事务就解决。
9. DICOM：tag=(group,element)，VR是类型，UID用途不同；Patient ID有命名空间。
10. 英文：一句结论、一个例子、一个边界；没有正式审计就如实说。
