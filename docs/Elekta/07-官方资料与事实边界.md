### MOSAIQ 与 SmartClinic 的区别

- **MOSAIQ：**上述官方资料中的肿瘤信息系统/电子健康记录核心产品。当前官网还使用 Elekta ONE OIS powered by MOSAIQ 的品牌表达；品牌名称不能推导实际代码版本。[Elekta ONE OIS](https://www.elekta.com/products/oncology-informatics/elekta-one/klas-recognition/)

## 3. DICOM、HL7、FHIR：面试入门到什么程度

| 名词 | 官方定义及入门区分 | 备考时抓住的问题 |
|---|---|---|
| DICOM | 医学影像及相关数据的通信和管理标准，涉及信息、协议和文件等，不仅是图片扩展名。[DICOM PS3.1 范围](https://dicom.nema.org/medical/dicom/current/output/chtml/part01/chapter_1.html) | 患者、检查和对象身份如何对应；缺失或重复对象怎么办；双方支持哪些对象和服务 |
| DICOM 放疗对象 | 例如 RT Structure Set 用于传输影像设备、模拟定位、治疗计划等系统定义的结构及相关数据。[DICOM PS3.3 RT Structure Set](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_A.19.html) | 能说出放疗交换不仅有影像，还可能涉及专门的结构/计划/剂量类对象；实际对象须以接口说明为准 |
| HL7 | HL7 是标准组织，也常泛指其标准家族；当讨论传统消息接口时，应明确是否指 HL7 v2。HL7 官方将 v2 定位为临床数据交换消息标准。[HL7 产品家族说明](https://blog.hl7.org/what_is_hl7_and_introduction_to_products_fhir_cda_v2) | 先确认版本与实施规范，再讨论字段映射、身份匹配、确认响应、重试和重复消息处理 |
| FHIR | HL7 发布的医疗信息交换标准，以 Resource 为基础；资源可组合、引用和扩展，存在能力声明和具体约束。FHIR 并不要求所有使用场景都必须采用 REST。[FHIR 官方概览](https://hl7.org/fhir/overview.html) | 了解资源、引用、Profile/约束和接口能力；不要把“返回 JSON”自动等同于符合 FHIR |

表格第三列是通用备考建议，不是 MOSAIQ 接口实现说明。

**推荐回答：**“DICOM 主要围绕医学影像及相关对象；HL7 是医疗信息交换标准家族，HL7 v2 是其中的消息标准；FHIR 也是 HL7 标准，采用资源模型。它们的用途有交集，可能在一个系统中并存。实际对接要确认版本、双方支持的能力和实施约束，不能仅凭标准名称判断能互通。”这是对上述官方定义的概括。

**能力边界说法：**“我目前是入门了解，能解释基本用途和接口工程问题，但没有真实医疗系统集成经验。”如果以后完成练习，再补充具体练习内容；不要改成“熟悉医疗行业协议”。

## 4. 医疗软件质量：理解用途，不背法规结论

| 标准 | 官方范围摘要 | 面试中可以联系的工程意识 |
|---|---|---|
| IEC 62304 | 医疗器械软件生命周期过程的框架。[官方标准目录](https://committee.iso.org/standard/38421.html) | 需求、设计、实现、测试、维护和变更之间需要有可解释的联系 |
| ISO 13485 | 医疗器械质量管理体系要求。[官方标准目录](https://www.iso.org/standard/59752.html) | 按团队质量体系执行评审、记录和受控流程 |
| ISO 14971 | 医疗器械风险管理，覆盖危害识别、风险评估、控制与控制有效性的关注。[官方标准目录](https://www.iso.org/standard/72704.html) | 不只看错误是否消失，还要考虑失效后果与修复是否引入新风险 |

第三列是备考理解，不是条款逐条解读。本次只核查公开范围介绍，未阅读付费标准全文。具体采用哪个版本、哪些修订和市场法规、产品分类以及适用范围，必须由团队质量/法规人员结合产品确认。JD 只明确 QMS 与适用法规要求，不能据此声称该岗位所有代码都必须满足某个特定认证或安全等级。

### 缺陷修复的回答顺序（备考推断）

1. 先确认影响范围、复现条件和潜在临床流程影响；按照团队机制升级重要问题。
2. 在合适的测试环境保留版本、日志、输入、时间线等证据，处理患者数据时遵守授权与数据保护流程。
3. 区分现象、直接原因、根因；用实验排除假设，避免“猜测性修复”。
4. 提交范围清晰的修改，评估相关模块、兼容性、数据迁移和异常路径。
5. 用回归测试与评审形成证据，按既定发布流程交付；保留关联记录并跟踪效果。

这是针对 JD 的演练框架，并非 Elekta 内部 SOP。RCA、纠正措施、验证活动和技术文档在 JD 中明确出现，因此值得用真实项目例子练习。

## 5. 面试时优先确认的事实

- 团队维护 MOSAIQ 的哪个模块与版本？开发工作中新功能、维护和客户问题调查大约各占多少？
- 主力语言及框架是什么？C++、C#、.NET 分别位于哪些模块？新人是否允许以 Java 基础迁移？
- 数据库、客户端/服务端划分、部署方式和外部接口范围是什么？
- 开发与质量工程师如何协作？需求、风险、测试和缺陷记录怎样关联？
- 英语会议、书面设计讨论和跨时区协作的频率如何？
- 入职前三个月期望新人独立完成什么？应届/1–2 年经验的评估口径是什么？

这些都是尚未由公开资料确认的问题，不要在自我介绍中提前回答为确定事实。
