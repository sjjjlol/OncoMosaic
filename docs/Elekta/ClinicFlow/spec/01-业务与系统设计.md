# 业务与系统设计

本文中的细化规则是已确认范围下的实施默认值。调整时同步测试和ADR，不需要为字段命名等普通实现选择重新开启需求访谈。

## 1. 用户流程与页面

预置预约人员Scheduler、任务人员TaskOperator、管理员Admin。预置虚构患者与资源，避免先做大量基础资料CRUD。

1. 登录后查看预约列表与资源可用时段。
2. 选择患者、一个资源、起止时间，创建Pending预约并立即占用时段。
3. 任务人员完成模拟前置任务；预约人员确认预约。
4. 可对Pending/Confirmed预约改期或取消，查看版本冲突和资源占用提示。
5. 详情展示任务、审计时间线和外部同步状态；管理员查看失败同步并重试。

前端至少包含：登录、预约列表、创建/改期表单、预约详情与任务、管理员同步队列、故障实验入口说明。操作成功后刷新真实服务端状态；409不能只弹“未知错误”。界面使用中文，保留英文业务术语对照。

## 2. 状态与不变量

预约状态：Pending、Confirmed、Cancelled。Pending允许确认或取消；Confirmed允许改期或取消；Cancelled为终态。改期后回到Pending并重置前置任务，旧任务完成记录通过审计保留。确认必须满足当前预约版本的所有必需任务。

任务采用简单的Pending/Completed；取消预约后不可继续完成任务。模拟任务例子为“资料核对”“预约信息复核”，不赋予临床决策含义。

核心约束：

- 每笔预约仅占一个资源，时长是15分钟整数倍；起止时间对齐时段，区间为[start,end)。项目默认机构时区Asia/Shanghai，数据库和API按UTC规范化，UI明确显示本地时间。
- Pending和Confirmed都占用资源。取消释放占用，但预约与审计仍保留。
- 每个(ResourceId, SlotStartUtc)最多有一个有效占用。
- 多时段预约、改期、取消、审计及相关Outbox写入具有同一数据库事务边界。
- 改期失败后旧时间、旧状态、版本和占用保持原状。跨资源改期适用相同要求。
- Version用于拒绝基于旧快照的修改。任务完成、确认、改期、取消与同一预约的并发操作必须序列化或检测冲突。
- 所有业务写操作有服务端权限校验；UI隐藏按钮不等于权限保障。

页面可限制单笔时长和可预约日期范围；具体限制以配置/规则及测试为准，不以未经确认的临床规范解释。

## 3. 模块与依赖

模块：Scheduling（预约/资源/任务）、Identity（演示账号与角色）、Audit、Integration（Outbox/外部同步）。API承接认证、参数和错误映射；应用服务编排用例与事务；领域规则表达状态和约束；基础设施负责数据库、时钟和HTTP等依赖。

保持业务边界清楚，避免为了分层为每个类机械添加接口。对外部HTTP、时间与故障注入等需要替换的依赖设置明确接口；业务规则尽量纯函数化。API、后台工作者使用同一套业务约束。

建议目录由开发者落地：backend、frontend、mock-external、tests、docs、labs、基础设施配置。一个主应用与一个模拟服务足够；后台任务可作为主应用HostedService运行。

## 4. 数据模型建议

| 实体 | 关键内容与约束 |
|---|---|
| User/Role | 演示账号、密码哈希、角色；成熟框架管理认证 |
| Patient | 虚构业务标识、显示名；无真实敏感数据 |
| Resource | 名称、类型、启用状态 |
| Appointment | PatientId、ResourceId、起止UTC、Status、Version、创建/修改时间 |
| SlotClaim | ResourceId、SlotStartUtc、AppointmentId；资源时段唯一约束 |
| PrerequisiteTask | AppointmentId、类型、状态、操作者、完成时间 |
| IdempotencyRecord | 主体＋操作＋Key唯一、请求指纹、结果引用/响应、生命周期 |
| AuditEntry | 对象、动作、操作者、变更摘要、时间、关联ID、对象版本 |
| OutboxMessage | MessageId、对象ID与版本、负载、重试次数、NextAttemptAt、租约及投递状态 |

Cancelled不通过给SlotClaim加状态而绕过唯一约束；有效占用表移除对应占用，历史由预约和审计维护。主表与占用表的一致性用事务及集成测试保护。

## 5. 预约竞争与改期事务

建议先用简单、可解释的MySQL方案：锁定受影响资源的稳定父记录，再检查/修改SlotClaim；数据库唯一约束是最终防线。单资源锁粒度较粗，但适合项目规模，需明确吞吐取舍。

建立所有写路径统一的锁顺序，例如先按ResourceId全序锁资源，再锁预约并验证其最新ResourceId/Version。用于决定锁集合的预读必须在锁后重新验证，变化时回滚并返回冲突或安全重试；不能将预读当一致性保证。任务/确认只锁预约时，也要保证不会再反向申请资源锁。

改期在同一事务中验证版本及状态、处理旧占用与新占用、更新时间/状态/任务、追加审计和Outbox。目标部分重叠自身旧时段必须正确处理。任何唯一冲突或错误回滚整笔事务。具体锁协议写ADR并通过并发测试验证；禁止只做“SELECT没有冲突→INSERT”而没有并发保障。

死锁/瞬时错误若重试，重试完整数据库事务且次数有限；事务内不执行外部HTTP，避免不可回滚的重复副作用。

## 6. API契约和幂等

建议端点：登录/登出/当前用户、患者/资源查询、资源可用时段、预约列表/详情/创建/改期/确认/取消、任务完成、审计查询、同步记录查询/重试。以OpenAPI记录实际端点与错误码。

写请求携带业务版本（创建除外）和Idempotency-Key。相同主体、操作和Key且负载一致，返回同一业务结果；相同Key但不同负载返回冲突。并发同Key仅允许一次业务变更。请求指纹需要稳定规范化；幂等键有效期及清理策略需明确，初版可保留不自动清理。

业务成功与幂等结果原子提交，事务回滚不能留下假成功。重放已完成请求应优先取得已保存结果，不因当前版本已改变而错误执行第二次。验证响应丢失后重试的行为。

建议状态码：401未认证、403无权限、404不存在、400格式错误、409资源/版本/幂等冲突。具体业务错误码可区分，前端应提供用户可采取的下一步。数据访问参数化、分页有上限、排序稳定，包含关联ID而不泄露内部堆栈。

## 7. Outbox与外部同步

本地业务事务写入预约状态与Outbox；提交后后台服务通过HTTP送到模拟外部服务。前端分别显示“预约本地状态”和“外部同步状态”，外部失败不假装本地事务未提交。

- 后台工作者采用作用域解析数据库依赖，传递CancellationToken；HTTP有超时，不能无限阻塞。
- 通过数据库原子领取/租约防止多个工作者同时随意处理一条消息。租约过期可恢复；标记完成/续租需校验领取标识。
- 持久化attempt与NextAttemptAt，指数退避并加抖动，达到上限进入待人工处理。永久性错误与可重试错误分开。
- HTTP调用在数据库事务外，允许重复投递；模拟接收端以MessageId持久去重，原子保存去重记录与业务效果。
- 同一预约消息携带单调版本号。选择完整状态快照，使接收端拒绝旧版本覆盖新版本；去重与版本处理均需要持久存储，重启后仍有效。
- 模拟“远端已保存但响应丢失”：本地重试沿用原MessageId，最终只有一次对应效果。取消/改期的新版本不能被旧请求覆盖。
- 管理员手动重试重置投递调度，保留历史且沿用同一消息身份。记录attempt、关联ID和错误摘要，日志不输出凭据。

这是至少一次投递＋接收端幂等，不声称端到端exactly-once。

## 8. FHIR练习边界

开发时从HL7官方文档核验并固定版本，建议以R4作为练习候选。选择Patient/Appointment中的最小明确字段集，做领域模型与FHIR资源的映射，并写契约测试。

FHIR示例端点与自定义Outbox投递协议分开命名和说明，不能将自定义messageId/version接口称作FHIR标准交互。若采用FHIR REST交互，必须按对应版本检查方法、资源标识及返回语义。文档列出支持内容、简化项和不支持能力；返回JSON不等于完整FHIR兼容。

## 9. 认证与审计

使用成熟.NET认证方案，演示账号由开发环境种子数据生成；密码哈希存储。开发者决定同源Cookie或其他合适方案，并处理相应CSRF/CORS/令牌安全问题，形成短ADR。实际凭据从环境变量或本机配置加载，仓库只提交示例。

Scheduler管理预约、TaskOperator完成任务、Admin查看全部与操作同步重试。权限矩阵通过API测试固定。审计记录与业务事务同步；只记录必要变化，普通角色不可修改/删除审计。应用层追加记录不等于实现了防篡改合规存储。
