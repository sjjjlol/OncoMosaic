# 开发与Git交付

## 1. 新会话启动

1. 阅读SPEC及关联设计、验收文档，检查实际目录、Git状态、远程和现有实现。继续已有进度，不覆盖用户修改。
2. 在ClinicFlow目录建立独立项目仓库，若已属于适合的项目仓库则沿用；只将本项目内容纳入Git，不把上级简历、面试笔记或JD截图推送。
3. 核实SDK、MySQL ARM镜像和数据提供程序兼容性，固定版本并记录ADR。GitHub仓库地址未提供时，请用户给出URL；若希望新建，则确认名称、归属和可见性后再创建。不能猜仓库或默认公开。
4. 仓库信息等待期间可完成本地开发。远程未配置/未授权时，将状态标为“本地完成，待push”；不得声称已远程交付。
5. 初始化开发进度文档，记录各里程碑状态、测试证据和下一步。用户已授权逐功能commit/push，目标明确后无需每次另行询问。

## 2. 功能切片与建议顺序

每个M项是独立可检查的交付切片；范围过大时拆成M3a/M3b等可运行子功能，不能把全部实现留到最后一次提交。学习时间是用户阅读练习预算，不要求开发助手每一天等待用户。

| 切片 | 交付内容 | 提交前主要证据 |
|---|---|---|
| M0 | 工程骨架、版本锁定、数据库/模拟服务启动、迁移、CI骨架、spec入库 | 干净启动、前后端构建、数据库连通 |
| M1 | 演示登录、角色权限、虚构患者/资源、基础前端 | A01/A18相关接口与页面验证 |
| M2 | 创建预约、多时段占用、幂等、列表/详情、审计 | A02–A04/A10–A11/A19 |
| M3 | 改期、取消、版本冲突及对应UI | A05–A08/A12；回归创建预约 |
| M4 | 前置任务与预约确认、角色完整流程 | A09/A18/A21 |
| M5 | Outbox、后台处理、模拟服务、持久去重、版本防倒退、同步UI | A13–A17；并发/重启/响应丢失测试 |
| M6 | FHIR小范围适配与契约文档 | A20；不破坏自定义同步协议 |
| M7 | 三个隔离故障实验与RCA材料 | 每个实验可复现、可重置、正常应用仍通过 |
| M8 | 升级演练、学习文档、独立任务、演示脚本、完整交付验证 | A01–A23证据完整；按新用户路径复验 |

M0建立CI，后续随功能增加测试；M2起产生Outbox记录，M5实现发送闭环。文档随功能更新，M8只补齐与整体验证，不能将全部测试和说明拖到最后。

## 3. 每个切片的提交与push闭环

1. 实现该切片，补相应测试、设计说明和Java对照。
2. 运行影响范围内的检查，记录实际命令及结果。检查diff，只暂存本功能文件。
3. 更新docs/development-progress.md：功能、验收ID、检查结果、已知问题、下一步。
4. 创建可读提交，例如`feat(scheduling): add atomic multi-slot booking`；实验使用`feat(labs): ...`，文档使用`docs: ...`。
5. 普通push到已经确认的远程与目标分支，验证远程分支包含本次提交。禁用force push、自动merge和未经要求的发布/tag流程。
6. 向用户报告功能、测试、commit短SHA、分支和push结果。若可查询GitHub Actions，核验该提交的结果；无法核验则明确“本地通过，远程CI待确认”。

建议在进度文档记录当前切片的待提交状态；提交SHA和push成功结果可在后续切片记录前一切片，并在最终交付报告集中列出，避免为把提交自身SHA写入自身而反复amend。Git历史/远程状态为提交事实来源。

push失败先检查错误，保留本地提交。认证或权限问题请用户处理，后续本地工作可继续；分支冲突先检查双方变更，不能reset或强推覆盖他人内容。远程CI失败后修复并提交，不能将失败切片标成全部完成。

## 4. 仓库内容边界

只提交项目代码、spec、虚构数据生成器、测试、学习文档、配置模板与锁文件。忽略真实.env、访问令牌、数据库卷、构建输出和本机私密配置。密钥使用环境变量或CI secrets；不得将整份个人简历作为项目README内容。面试讲稿中的个人经历默认保存在上级Elekta材料中，仓库文档聚焦项目。

目标分支尊重用户选择/已有仓库约定；空仓库可提议main但须以实际配置为准。用户未要求PR，不必为每个切片另建PR；若之后要求，沿用项目规范。

## 5. 项目级完成报告

列出：启动方式、各功能状态、A01–A23实际证据、故障实验结果、远程地址与各功能提交、远程CI状态、学习入口和未完成项。所有push均完成且验收满足后，才能说“开发与远程交付完成”。只完成代码或本地测试时如实报告阶段状态。
