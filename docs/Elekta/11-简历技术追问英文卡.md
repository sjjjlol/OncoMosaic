# 简历技术追问：简单英文与架构师深挖

依据当前 Elekta 文件夹中的简历 PDF、02/08 项目事实底稿、OncoMosaic 项目指南和英文话术。简历是主张，旧笔记是解释，当前代码是近期实现证据；三者不自动证明历史交付时间与指标。

## 1. 退款：二面主故事（2026-10-10按完整方案校准）

主依据：退款消费者完整故事与技术方案（外部个人笔记，未收录于本仓库）。原材料区分了源码片段、选定还原和合理补全，本节沿用这个边界。

### 先理解业务链路

```text
附加产品业务写退款表
→ Binlog监听产生单条refundId消息
→ 消费者查询当前退款和其他可合并退款
→ 完整集合形成后统一排序
→ 第一把锁开始，逐笔竞争整组处理权
→ 调用订单中心退款接口，回写结果

未完成记录 → 定时扫描 → 重发原refundId消息 → 同一个消费者
尚未提交且超过配置时限 → 当前记录单退（仍用同一明细锁规则）
```

X平台处理附加产品，不把主票加入本次合并。金额由上游业务确定，消费者不重新执行供应商退订。目标是减少对订单中心的分散退款调用；不能额外声称支付调用或用户通知减少了多少。

### 约90秒英文主回答

> At Ctrip, I worked on **combined refunds** for extra products in train orders.
> **Each refund record  produced its own message**. The change was inside the consumer: **one message could trigger a group of refunds instead of just one.**
> The goal was to **reduce separate calls to the order center**.
>
> Different messages could lead to the same refund group in different orders.
> One worker could lock refund 1 first, while another locked refund 2 first. Both could then **fail to get the remaining lock and return without submitting the refund**.
> My main fix was to **sort the full group** **by refund ID** **before taking the first lock**. Sorting only the other records would not be enough.
>
> Unfinished records could be sent back to the same consumer by a scheduled scan.
> If a refund had not been submitted and passed the time limit, it could use the **single-refund fallback**.
> The order change addressed the lock conflict. Duplicate effects still needed separate **safeguards**.

简短结论已足够；“不是永久阻塞死锁”和具体组装路径留给追问。若要解释所选还原，用下面的话，不把未取证细节直接归为历史事实。

### 为什么两条消息会产生反序：具体还原例子

> A useful way to explain the conflict is to **put the current refund first, then add the other refunds**.
> The message for refund 1 gives [1, 2]. The message for refund 2 gives [2, 1].
> Even if the other records are sorted, the full groups can still differ.
> That is why the full group must be sorted before any lock is taken.

**事实边界：**“当前＋其他、当前置顶”是完整方案选定的演进还原，尚未由组装源码或日志证实。可以用于理解和白板推演，不能说已通过生产源码确认。排序、逐笔抢锁、失败return、成功Key检查、创建时间加配置时限后的单退分支，是原文列为片段直接支持的部分；本轮没有重新读取那些附件取证。

### 白板交错

```text
消息M1（refundId=1） → 还原组装 [1,2]
消息M2（refundId=2） → 还原组装 [2,1]

初版：A拿R1 → B拿R2 → A拿R2失败返回 → B拿R1失败返回
修复：组装完整集合 → 都排序成[1,2] → 才开始第一把锁
      A、B先争R1 → 失败者退出 → 获胜者继续尝试R2
```

**绝不能：**先锁当前记录，再查其他记录和排序。这样A、B已经各拿不同锁，后续排序无法修复起始冲突。其他持锁者、部分重叠或租约失效仍可能让本轮无法取得全组；统一顺序不是“每轮必然成功”。

### 高频追问

| 问题 | 简单英文回答 | 必须理解 |
|---|---|---|
| Were messages merged upstream? | No. Each message still carried one refund ID. The consumer built the group. | 改造点在消费者处理范围 |
| Why could the order differ? | In the reconstructed flow, **each consumer puts its current refund first and then adds the others**. Different current records can produce different full orders. | 具体拼接是还原，不是SQL随机返回的已证实根因 |
| Why not just ORDER BY in SQL? | Sorting the other records does not sort the current record together with them. I need one order for the full group. | 子列表有序不等于整组一致 |
| Can you lock the current refund first? | No. The full group must be built and sorted before the first lock. | 排序前不能已持组内锁 |
| Is this a classic deadlock? | Not a permanent blocking deadlock. Lock failure made the worker return, and the locks had an expiry time. | 反复竞争与停滞，不是线程永久等候 |
| How does work continue after return? | A scheduled task scans unfinished records and sends the original refund ID again to the same consumer. | return本身不等于MQ自动重试 |
| Does the worker wait for 300 seconds? | No. It checks the record's creation time on each attempt. The configured limit in the example is 300 seconds. | 不是线程sleep，也不每次重置计时；扫描有延迟 |
| What if only one candidate remains? | If the relevant product results are clear, one valid refund can be submitted. It does not need a second record. | 就绪范围定义是方案补全，不是查到两条就全齐 |
| What if the group was already submitted? | I would track the existing result. I would not create a new single refund just because the time limit passed. | 已提交/未知结果先核对；时限只兜底尚未提交 |
| Does sorting prevent duplicate refunds? | No. It fixes the order problem. The downstream service still needs to recognize the same refund details across retries and fallback paths. | 稳定明细身份，不能只认新批次请求号 |
| What if the lock expires? | Another worker may enter while the first is still running. The downstream duplicate check still matters. | TTL不是最终资金保障 |
| What if the refund call times out? | The result may be unknown. I would check the existing refund result before retrying and keep the same refund identities. | 不换流水盲目重付；下游能力未核实 |
| Why not one order-level lock? | It may be simpler if the group boundary is stable. I would compare contention and check every entry point. | 选型取决于范围与入口 |
| What if one lock fails? | I would avoid submitting the group and release only the locks owned by this attempt. | unique token与原子校验删除是完善方案，不是已证实原实现 |

### 如何解释“什么时候可以合并”

完整方案选择：本次涉及的附加产品处理结果明确，选尚未提交、支付维度与币种等兼容的待退明细；已明确无需退款的产品不用等，尚在处理或应退记录未生成则等待后续消费。这个就绪规则是合理补全，不是已核验原实现。

> In this design, I would wait until the relevant product results are clear.
> I would combine only compatible, unsubmitted refund records.
> I would not assume that all records have arrived just because a query returns two rows.

### 如何验证：分清修复前后的屏障

> I would start two tasks from different refund IDs and let each task build its own group.
> In the old flow, I would control the timing so both tasks get their first lock before trying the second.
> In the fixed flow, both should compete for the same first lock. I would not require both to acquire it before continuing.

修复版不能沿用“双方都拿到第一把锁后放行”的屏障，否则测试自己卡住。验证组装→完整排序→第一次加锁的顺序；检查是否提交退款，而非只检查列表排序。再覆盖条件未齐、扫描重投、超时单退、已受理但超过时限、旧消息、部分重叠、TTL过期。

### 个人改动与方案补全分开

> My main contribution was the **consistent lock order** at the final entry point.
> State checks, safe lock release, and downstream duplicate handling are separate parts of a complete solution.
> I would explain which parts were implemented and which parts are design improvements.

原文附件锁值为固定"1"，释放未展示。不能把安全token释放、获全组锁后重新读状态、成功Key写入位置、结果未知持久化等都说成自己已上线的功能。下游按稳定明细防重与查询能力是方案依赖，不是已证实的订单中心实现。

**最值得记的一句：**

> Build the full group, sort it, and only then take the first lock.

## 3. API迁移：兼容性与渐进变更

### 约45秒

> I helped **retire** about one hundred inactive APIs and **migrate** about ten active read APIs.
> The key goal was to keep the behavior expected by existing callers.
> We **compared old and new read responses and switched traffic gradually**.
> I paid attention to default values, empty results, ordering, and errors.
> Both services used the same database, so this was a service migration.

| 追问 | 简单英文 |
|---|---|
| Is HTTP 200 enough? | No. The values, ordering, and error meaning also need to match the contract. |
| Can you mirror a write? | A second call may cause a second effect. I would not mirror writes without a safe design. |
| Why can two read results differ? | The data may change between reads. I would separate timing differences from logic differences. |
| How do you know an API is unused? | I would check a suitable time window, scheduled jobs, and callers. A short quiet period is not enough. |
| Did you build the migration platform? | I participated in the migration work. I did not build the whole mirror or traffic-switching platform. |

需要个人补充：具体哪个接口、一个响应差异、自己的代码改动、实际验证方法。若没有真实差异案例，可讲检查维度，不编“当时发现了某字段”。

## 4. 肿瘤研究平台：最适合展开的.NET项目

### 约60秒

> This is a research platform for **analyzing tumor tissue images**.
> Users **select a region, run analysis, review objects, and export results**.
> The frontend uses React. The business backend uses ASP.NET Core and MySQL.
> A separate Python service handles image processing.
> The main design points are background jobs, clear data rules, and versioned results.
> For example, an export uses the review version that the user checked, even if a later review is added.

**历史与当前复现必须先核对：**简历时间写2022年；当前仓库的模拟算法和完整版本流程可能是近期复现。按实际情况分别使用：

> The original research project was in 2022. In the current implementation, ...

只有确实是本人近期重建时才说：

> I later rebuilt parts of the workflow with the current stack.

当前仓库使用合成数据和确定性模拟分析流程，不代表临床验证或本人训练了医学模型。该范围依据现有项目文档，不是本轮重新进行源码审计。

### A. Why split .NET and Python?

> The .NET service **manages the workflow and stored results.**
> Python **handles image analysis**.
> This keeps the data contract clear and allows the analysis code to change separately.

重点：跨服务需明确输入身份、runId、产物引用和错误语义；分服务不会自动解决一致性。

### B. Why background jobs? / What if the process restarts?

> Image analysis may take longer than a normal web request.
> The API **stores a job and returns its ID**.
> **A worker runs the job and stores the result**.
> **Persistent state helps the system find unfinished work after a restart.**

追问并发扩展：

> The current design has one worker. More workers would need an atomic claim and a way to handle expired claims.

**懂到这一层：**数据库存任务 → 单 worker 调度 → Python结果完整发布 → .NET验证manifest → 结果和成功状态同事务登记。重启重新尝试不等于新增一批对象；任务启动数不是“恰好执行一次”保证。

### C. Python succeeds but database save fails?

> I would keep a stable run ID and input identity.
> A retry should reuse a complete result for the same input when possible.
> The backend still validates the result before saving it.
> Saving the objects and marking success should happen in one transaction.

文件发布与数据库不是同一个原子事务；需要识别中间窗口。是否实际复用、如何校验，按当前文档和自己的理解说明，不说“用了分布式事务”。

### D. What if two users review the same result?

> **Each change includes the version the user read**.
> The s**erver checks it before saving a new review**.
> **If the version is old, it returns a conflict**.
> We keep the original result and add review changes instead of losing the history.

当前材料描述：事务锁任务行 → 检查base version → 分配新版本；这是版本前提与行锁的组合，不是仅靠前端版本数字就安全。

### E. Why fixed versions for export?

> The page and the download are separate requests.
> Reading the latest result twice could give different numbers.
> An explicit review version keeps the report tied to what the user saw.

白板例子：页面 A(v4)/B(v7)，随后 A→v5，导出仍用v4/v7。MySQL可重复读事务解决同一次比较的两侧读取视图；跨请求一致性依靠显式版本，不能依靠“每次都开事务”。

### F. Explain Ki-67 rules without difficult English.

> Cell identity and Ki-67 status are separate fields.
> A result can be positive, negative, or not available for evaluation.
> The positive rate uses only the valid objects in the chosen group.
> An unknown result is not treated as negative.

教学例：目标群100个，阳性30、阴性60、无法判定10；阳性率30/90，覆盖率90/100。实际未检测与无法判定可再区分。分母为0时返回不可计算，而非0%。“研究统计规则”不代表临床诊断标准。

### G. Explain image coordinates.

> The analysis uses coordinates inside the selected region.
> The viewer uses coordinates in the full image.
> I add the region offset before drawing objects on the image.
> The image, contours, and lines use the same zoom and pan transform.

例：ROI原点(100,200)，局部点(10,20)，原图点(110,220)。像素距离转换物理单位还需可靠比例尺。

## 7. 招行RAG / MCP课题

### 约45秒

> I worked on a knowledge search project for **internal technical documents**.
> The pipeline **parsed documents, split them into chunks, and updated the search indexes.**
> Search combined keyword matching with vector search.
> I **exposed the search tools through a local MCP server** so an agent could use them.
> I focused on useful sources and results that could be checked.

| 追问 | 简单英文 |
|---|---|
| Why keyword and vector search? | **Exact names and error codes** need **keyword matching**. **Vector search** helps when the **question uses different words**. |
| What does RRF do? | **It combines ranked lists without requiring their raw scores to have the same scale.** |
| Why rerank? | It **reviews a smaller candidate set to improve the final order**, with extra time and cost. |
| How do updates work? | **Stable chunk IDs and content hashes** help detect changes and **avoid duplicate entries**. |
| Are two indexes automatically consistent? | No. Partial updates need a recovery plan. I would check both indexes against the same document version. |
| What is MCP here? | It is a standard tool interface for the agent. It is not the retrieval algorithm itself. |

简历写约1000文档、约200评测问题和多项分数。追问要说明生成、抽检、分层、评测配置、版本、是否有固定测试集与泄漏风险；评测分数不是线上可靠性保证。现有资料不支持大规模部署、跨组商业推广或正式审计。

## 8. 保险接口优化：备用且需核对

> The design idea was to **avoid repeated calls within one request** and **run independent calls with bounded concurrency**.
> I would keep pagination and error behavior consistent.
> I would also measure tail latency and downstream load.

这段只讨论设计。若确认简历里的实施是本人完成，可改过去式并补具体调用链；未确认前不要背P95数字。
