# 二面现场编程与数据库接口测试

练习目标：用简单英文解释需求、写小实现、测试行为、承认边界。用户已确认现场可用Java，因此主练Java；C#用于.NET框架和简历追问。以下练习是模拟任务，不是已确认的 Elekta 现场题。

## 1. “为简单数据库接口设计测试”先问什么

> What operations does the interface support?
> **What should happen for a missing record or duplicate key?**
> **Does a write need a transaction?**
> **Can two callers update the same record?**
> Are retries supported, and how is a repeated request identified?

未提供接口时，自己给一个小契约并请对方认可，不要直接假设所有数据库的行为相同。

### 本练习的契约

```java
interface AppointmentStore {
    Appointment get(int id); // 缺失返回null；契约须明确
    boolean add(int id);
    UpdateResult transition(int id, long expectedVersion, Status target);
}
```

- ID必须为正；非法ID、版本或null状态抛IllegalArgumentException。
- Add新记录：Pending、Version=1；已存在返回false，不覆盖。
- get缺失返回null；返回不可变值，不让调用方修改内部状态。
- Transition只允许Pending→Confirmed或Pending→Cancelled。两者在此练习中都是终态；这是题目约定，不是完整预约业务。
- 更新需匹配版本；成功版本加1；失败不改数据。
- 同一个版本的并发更新最多一个成功。
- 错误优先级：参数非法（含null状态）→不存在→版本冲突→状态非法→原子提交。
- 不提供删除、列表、审计或网络重试。练习实现是内存对象，不声称支持真实数据库事务。

关键：先明确“重复确认返回成功还是错误”。本练习选择状态非法；如果API要求请求幂等，应在接口边界识别同一请求并返回原结果，不能简单混同重复状态转换。

## 2. 逐项测试矩阵

| ID | 输入/场景 | 期望 | 证明什么 |
|---|---|---|---|
| T01 | Get(不存在ID) | null | 缺失契约 |
| T02 | Get/Add ID=0 | 参数异常，无写入 | 输入边界 |
| T03 | Add(新ID)，再Get | Pending / v1 | 正常创建与读取 |
| T04 | 同一ID再次Add | false，原记录不变 | 唯一性与不覆盖 |
| T05 | Pending v1→Confirmed | Updated，Confirmed/v2 | 正常转换 |
| T06 | 用旧v1更新 | VersionConflict，数据不变 | 防止丢失更新 |
| T07 | Confirmed v2→Confirmed | InvalidTransition | 重复状态动作 |
| T08 | Cancelled→Confirmed | InvalidTransition | 非法逆向转换 |
| T09 | 不存在ID更新 | NotFound | 明确区分缺失 |
| T10 | 版本0或null状态 | 参数异常 | 不信任外部输入 |
| T11 | 两线程读v1，同时提交不同终态 | 1成功+1冲突，最终v2 | 原子比较并更新 |
| T12 | 保存后检查此前读取对象 | 旧快照仍Pending/v1 | 不泄漏可变内部对象 |
| T13 | 失败操作后检查状态/版本 | 都不改变 | 失败不留下部分状态 |

不仅断言返回值，还断言最终数据和副作用次数。测试命名如 `StaleVersion_DoesNotOverwriteConfirmedRecord`，比 `Test3` 更能解释风险。

## 3. 真实数据库需要额外测试

上述内存练习不能证明下面的行为。若面试给 SQL Server/MySQL，使用对应引擎、独立连接和清理策略做集成测试。

| 场景 | 安排与执行 | 验收 |
|---|---|---|
| 唯一约束 | 两个连接同时插入同一业务key | 最多一条，错误映射清楚 |
| 版本条件更新 | 两连接先读v1，再通过屏障提交 | 一次影响1行，一次0行，最终v2 |
| 多表原子性 | 更新业务行，插审计/关联行前触发失败 | 两者一起回滚，无部分提交 |
| 精度与时间 | decimal金额/UTC或offset/Unicode文本往返 | 存取符合契约，不用double存金额 |
| 隔离与读视图 | 两事务按确定交错读写 | 结果符合所选隔离与配置 |
| 连接失败 | 提交前断开与提交后响应丢失分别测试 | 区分确定失败和结果未知 |
| 参数化 | 文本包含引号及SQL片段 | 作为值处理，不执行额外SQL |
| 分页 | 相同StartAt，不同Id；插入新数据 | 明确排序与一致性契约 |
| 升级 | 历史数据、脚本失败、脚本重复执行 | 版本兼容与恢复符合设计 |

**不要这样测试：**两个 `Task.Run` 加 `Sleep(100)`，然后宣称一定发生指定交错。用屏障/事件控制“都读完旧值”后再开始写，设超时防挂死。真实数据库两个写者不能共用同一个连接、事务或ORM上下文；否则不是实际并发。

每个测试独立数据或独立数据库；并发参与者需要共享该用例的数据。只用外层事务包住测试可能让独立连接看不到数据；准备数据先提交，最后清理。集成测试应验证与生产相同引擎的重要行为，SQLite或EF内存提供程序可能有差异。[微软 EF Core 测试策略](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy)

英文收尾：

> **Unit tests** **check rules quickly**.
> **Integration tests check the real database behavior**.
> For each failure, I check the stored state as well as the returned error.

## 4. 35分钟实操：实现接口与状态更新

**题目英文：**

> Implement a small appointment store. A new appointment is pending. It can be confirmed or cancelled once. Updates must include the version that the caller read. Define the error cases and write tests.

**时间分配：**0–4分钟契约，4–8分钟类型，8–23分钟实现，23–31分钟测试，31–35分钟解释限制。

**先自己写，再看参考：**[Java参考实现](二面现场编程练习/InterviewPractice.java)；[C#对照](二面现场编程练习/Program.cs)。运行方法见[README](二面现场编程练习/README.md)。文件包含参考实现和行为检查，不需要数据库或NuGet测试包。

最小设计：不可变Appointment记录、Status枚举、UpdateResult枚举、小接口、内存实现。Java `ConcurrentHashMap.replace(key, oldValue, newValue)`做原子条件替换；C#的`ConcurrentDictionary.TryUpdate(key,newValue,oldValue)`同样做原子条件替换；普通 `Get→if Version matches→赋值` 仍会有竞争窗口。

**边写边说：**

> I will define the allowed states first.
> I will return a clear result for a version conflict.
> The version check and the update must be one atomic operation.
> I will test one normal update and one stale update before adding more cases.

**解释限制：**

> This version stores data in one process.
> It is not persistent and does not test database transactions.
> A real database implementation would use a conditional update and check the affected row count.

数据库对应，Version是应用整数，SQL使用参数而非字符串拼接：

```sql
UPDATE Appointment
SET Status = @target, Version = Version + 1
WHERE Id = @id AND Version = @expectedVersion AND Status = 'Pending';
```

`@target`需先验证只能Confirmed/Cancelled。0行可能是缺失、版本不匹配或状态不合法；若要精确错误分类，需要定义额外查询的一致性和并发语义。不要宣称这一句就能区分所有错误。

### C# 对照（框架追问用）

| C# | Java侧理解 |
|---|---|
| sealed record | 不可变record/值对象 |
| nullable Get结果 | nullable返回或Optional，先定义契约 |
| TryUpdate(key,next,old) | ConcurrentHashMap.replace(key,old,next) |
| enum result | 显式业务结果枚举 |
| virtual/override | C#要显式virtual；Java普通可重写实例方法规则不同 |
| using IDisposable | try-with-resources / AutoCloseable |
| async Task | 异步结果概念相通，不能把语法与线程模型直接等同 |

现场已允许Java，主练沿用该模型；并发映射必须原子替换，值对象保持不可变。熟悉业务契约比逐字翻译API更重要。

## 5. 其他非算法现场任务

### A. 25分钟：重构重复供应商请求代码

两个产品都“校验→解析站点→构建请求→发送”，站点规则不同。先识别是否只是规则变化，再选择组合策略或模板方法。新增第三种服务时公共流程不复制。

验收：两种正常输入、一个非法输入；供应商失败不返回假成功；说明为什么抽象。不要建立五层继承。

> The flow is stable, but the station rule varies. I would keep the rule separate so it can be tested on its own.

### B. 30分钟：处理重复消息

输入MessageId、AppointmentId、Action。先确认MessageId的唯一范围、重复内容变化、是否要求重启后有效。持久化唯一约束和业务变更同事务；相同key不同内容拒绝。内存HashSet只能作为局部演示。

验收：同消息重复、两个并发重复、相同ID不同内容、处理后ACK前故障。外部通知须明确其幂等/查询契约；本地事务不能覆盖远端动作。

> A retry may happen after the business change succeeds. I need to identify the same request and return its stored result.

### C. 25分钟：改一个查询/API

实现分页列表，增加状态过滤和错误处理。先定义合法page size、排序及空结果。参数化查询，唯一决胜字段；不无限返回或把分页后结果再随意过滤。

验收：空列表、相同时间、非法分页、过滤、缺失权限、数据库失败。若任务只让写纯函数，不增加数据库框架。

### D. 20分钟：写测试而非实现

给一个服务，写正常、缺失、冲突、依赖失败、重复请求测试。stub控制已知依赖响应，spy核对调用次数；不mock整个服务内部实现。数据库锁与SQL翻译另做集成测试。

## 6. 15分钟代码评审/修复题

```csharp
// 故意错误的练习片段，不用于实际实现
var row = store.Get(id)!;
if (row.Version == expectedVersion)
{
    db.UpdateStatus(id, "Confirmed");
    supplier.Send(id); // 无明确请求ID；结果可能未知
}
return "OK";
```

找具体失败路径：

1. 缺失记录导致空引用，版本冲突却仍返回OK。
2. 检查和写入不原子，两者都读v1可能都更新。
3. 没有状态前置条件，Cancelled也可能被Confirm。
4. 本地已改而supplier失败；远端成功但超时后重试可能重复。
5. 缺少业务错误语义、结果未知处理与验证。

英文review：

> Two callers can both pass this check before either update is saved.
> Could we move the version condition into the update and check the affected row count?
> The supplier call also needs a clear retry contract because a timeout does not prove failure.

修复先明确业务是否需要外部调用；再考虑原子状态更新、稳定请求ID、待同步状态或outbox。不要以加一个应用进程lock解释跨进程安全。

## 7. 写完后自查

- 能按需求跑一个正常流程吗？
- 非法输入、缺失、状态冲突和版本冲突有明确行为吗？
- 失败是否保持数据不变？
- 并发检查是否与写入原子绑定？
- 能在不看参考时解释每个类型的作用吗？
- 能说出“此练习没有验证什么”吗？

拿到题后优先完成主路径和关键失败测试，再讨论扩展；不要一开始安装大量框架或搭完整分布式系统。
