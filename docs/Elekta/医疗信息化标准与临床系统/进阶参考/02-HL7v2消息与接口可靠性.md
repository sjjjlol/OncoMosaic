# HL7 v2：从读消息到可靠处理

## 1. HL7 不等于 HL7 v2

HL7 是标准组织与标准家族的称呼；FHIR 也是其标准。面试官说“HL7 接口”时，可先确认是否指 v2、版本号、消息类型和实施规范。本章使用 v2.5.1 的传统分隔符消息教学，不涵盖全部 HL7 标准。

| 常见消息/事件 | 入门用途 | 边界 |
|---|---|---|
| ADT | 患者管理及就诊相关事件 | 具体由事件决定，不是所有 ADT 都等于入院 |
| ADT^A01 | 入院/就诊通知 | 本章示例采用这一事件 |
| ADT^A08 | 患者信息更新 | 更新哪些字段、空值含义仍要按契约 |
| ORM^O01 | 一般医嘱消息的经典例子 | v2.5.1 保留用于向后兼容，推荐更专门的 OMG/OML/OMI 等消息 |
| ORU^R01 | 非请求式观察结果报告的经典例子 | 结果需要编码、类型、单位、状态等信息 |

依据：[HL7 Europe 官方域 v2.5.1 患者管理](https://hl7.eu/HL7v2x/v251/std251/ch03.html)、[医嘱](https://hl7.eu/HL7v2x/v251/std251/ch04.html)、[观察结果](https://hl7.eu/HL7v2x/v251/std251/ch07.html)。本文列举用途，不据此认定 MOSAIQ 使用某一消息。

## 2. 一个可逐字段讲解的消息

以下全是虚构数据；是学习用简化示例，尚未按任何医院 Profile 验收。显示为多行便于阅读，实际传统消息的段结束符为 CR（回车），不应简单把屏幕换行当作线上字节。

```text
MSH|^~\&|HIS|HOSP_A|OIS|ONC_A|20261002090000+0800||ADT^A01^ADT_A01|MSG-0001|T|2.5.1
EVN|A01|20261002090000+0800
PID|1||P0001^^^HOSP_A^MR||TEST^PATIENT||19800101|U
PV1|1|I
```

| 段/字段 | 示例 | 意义 |
|---|---|---|
| MSH | 消息头 | 谁发送、谁接收、类型、ID、版本等 |
| MSH-1 / MSH-2 | `|` / `^~\&` | 字段分隔符与其他编码字符 |
| MSH-3/4 | HIS / HOSP_A | 发送应用、发送机构 |
| MSH-5/6 | OIS / ONC_A | 接收应用、接收机构 |
| MSH-7 | 带 `+0800` 的时间 | 消息时间；不是可靠的业务更新序号 |
| MSH-9 | ADT^A01^ADT_A01 | 消息类型、触发事件、结构 |
| MSH-10 | MSG-0001 | 消息控制 ID，用于消息关联 |
| MSH-11 | T | 教学示例中的训练处理标识；生产契约另行确定 |
| MSH-12 | 2.5.1 | 版本 |
| EVN | 事件信息 | 事件类型/记录时间等 |
| PID-3 | P0001^^^HOSP_A^MR | 患者标识列表；本例含编号、签发机构和病历号类型 |
| PID-5 | TEST^PATIENT | 姓名组件，不能当成唯一键 |
| PV1-2 | I | 示例患者类别；不是患者编号 |

`|` 分字段，`^` 分组件，`~` 表示重复，`&` 分子组件，`\` 用于转义。MSH 有特殊编号规则：字段分隔符本身就是 MSH-1。不要用普通数组下标套路直接解析 MSH，也不要用几次 split 冒充完整解析器。[v2.5.1 控制与编码规则](https://hl7.eu/HL7v2x/v251/std251/ch02.html)

**记忆：**MSH-10 回答“哪一条消息”；PID-3 回答“哪个标识域的患者”；PV1 的就诊信息回答“哪一次业务上下文”。三者不是同一个 ID。

## 3. ACK：确认的是哪一步

对应的简化确认示例：

```text
MSH|^~\&|OIS|ONC_A|HIS|HOSP_A|20261002090001+0800||ACK^A01^ACK|ACK-0001|T|2.5.1
MSA|AA|MSG-0001
```

ACK 自己的 MSH-10 是新消息的 ID；**MSA-2** 才回显被确认消息的 MSH-10。不能把 ACK 的 MSH-10 直接等于原消息 ID。

| 代码 | 学习时的理解 |
|---|---|
| AA / AE / AR | 应用确认：接受 / 错误 / 拒绝；按原始或增强模式规定解释 |
| CA / CE / CR | 增强模式的接收确认：提交接受 / 错误 / 拒绝 |

原始确认模式与增强模式不同；增强模式可区分接收确认和应用确认，MSH-15/16 控制相应确认要求。CA 不能被解释为所有下游业务已经完成；AA 也不能被扩展解释为整个临床流程已完成。确认边界须写在接口契约里。[v2.5.1 确认规则](https://hl7.eu/HL7v2x/v251/std251/ch02.html)

如果采用“持久化到 Inbox 后再异步处理”的设计，要和对端明确确认模式与状态查询/错误反馈，不能刚写进内存队列就返回一个表示应用完成的 AA。

## 4. MLLP 与消息模型分别管什么

传统 v2 接口常见 MLLP（Minimal Lower Layer Protocol）承载，通过起止字节包裹消息。它处理消息边界，不提供患者身份匹配、应用幂等或完整安全方案。TCP 有序不保证跨连接重发、多个发送源和异步业务处理后的状态永远有序。MLLP 教学参考及页面状态见[来源文档](../05-官方来源与事实边界.md)。

不用记“HL7 永远走 TCP”；真正应确认的是传输方式、连接策略、超时、确认与重试规则，以及安全部署要求。

## 5. 面试常用的处理链路

下述是通用工程设计建议，不是 v2 标准强制的数据库架构，也不是 MOSAIQ 实现。

```text
接收 → 解析与版本检查 → 契约/字段校验 → 持久接收记录
     → 去重与身份匹配 → 业务规则/事务 → 结果与审计 → 约定的确认/反馈
```

| 问题 | 设计/调查重点 |
|---|---|
| ACK 丢失，对端重发 | 用来源应用/机构＋消息控制 ID 等约定作用域识别重发，保存处理结果；跨来源不能只靠裸 MSH-10 |
| 同一去重键、不同载荷 | 检测冲突并隔离，保留证据；不能直接忽略或覆盖 |
| 发送方换 ID 重发同一业务 | 消息去重不足以保证业务幂等，还需患者/就诊/医嘱等业务规则 |
| 更新乱序 | 明确权威来源、字段所有权与更新规则；没有可靠版本时不凭接收时间猜新旧 |
| 患者 A/B 编号碰撞 | 看签发机构/标识域；存在歧义时进入核查流程 |
| 合并患者 | 使用约定的合并事件及规则评估引用、历史和审计，不做简单批量改主键 |
| 中文乱码 | 核对消息字符集约定、MSH-18 与接收端配置，不盲目改成 UTF-8 |
| 空字段、缺字段、显式空值 | 传统编码中含义可能不同，更新语义需按标准和接口约定解释 |
| 结果代码与单位 | 核对 OBX 的类型、代码系统、数值/文本、单位和结果状态，不能只存一个字符串 |

字段定义可查[控制章](https://hl7.eu/HL7v2x/v251/std251/ch02.html)与[结果章](https://hl7.eu/HL7v2x/v251/std251/ch07.html)。去重键和状态规则是工程建议，须用实际接口规范确定。

## 6. 可靠性测试怎样说得具体

至少覆盖：成功处理但 ACK 丢失、同消息并发两次、事务失败后重试、服务重启、同键不同内容、老更新晚到、患者域冲突、非法编码、缺必填字段。验收不能只看“收到 ACK”，还要检查业务效果次数、最终状态、错误反馈与可追溯记录。

和 Java 经验连接：你已经熟悉的事务、唯一约束、Inbox/Outbox、重试和审计可用于实现接口可靠性；患者语义、确认模式和临床状态必须重新学习，不能把普通订单更新规则直接套到患者数据上。
