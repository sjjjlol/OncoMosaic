# Elekta｜医疗信息化面试问答与动手练习

题目按 JD 和标准设计，**不是已核实的 Elekta 真题**。标准事实依据前面三章及[官方来源](../05-官方来源与事实边界.md)；故障处理方案是通用软件工程练习，不代表 MOSAIQ 内部流程。

## 1. 开场：诚实而有内容的 60 秒回答

**问：你了解 DICOM、HL7、FHIR 吗？**

> 我目前是学习入门，没有真实医疗系统生产集成经验。DICOM 面向医学影像及相关数据，也包括放疗的结构、计划、剂量等对象。HL7 是标准家族，传统 v2 接口通常以患者、就诊、医嘱和结果等消息驱动系统交互；FHIR 同属 HL7，以资源模型组织数据。我准备时重点关注了患者身份和标识域、DICOM 对象引用、v2 确认模式，以及 FHIR 资源身份、能力声明和版本控制。实际对接时，我会先核对版本和实施约定，再讨论映射、重复与乱序处理、错误反馈和验证证据。

完成后面的练习，才可以追加“我用虚构数据做过某项练习”，并说出输入、操作和验收结果。仅阅读本套文档时，不说“完成了医疗接口项目”。

## 2. 基础概念问答

### Q1. 三个标准是不是分别等于图片、消息、JSON？

**参考答案：**可以把它当初步记忆，但不够准确。DICOM 不仅是影像文件；HL7 也不只有 v2；FHIR 不仅是 JSON 或 REST。标准不仅规定表达形式，还规定信息模型、交互与约束。实际互通需要核对版本、双方能力和具体实施规范。

**追问：**FHIR 能替代 DICOM 像素交换吗？不要直接说能；FHIR 可描述影像检查和访问相关信息，像素获取等仍可通过 DICOM/DICOMweb。具体看应用契约。

### Q2. MOSAIQ、TPS、PACS 怎么区分？

**参考答案：**本岗位围绕 MOSAIQ 肿瘤信息与工作流管理。TPS 是治疗计划系统，PACS 负责影像归档与通信。它们可能互相交换数据，但承担不同职责。我不会将 MOSAIQ 简单描述为计算剂量的 TPS，具体模块还要向团队确认。

### Q3. 为什么患者编号相同不能直接匹配？

**参考答案：**编号有签发域，不同医院可以有相同编号。同一患者也可能有多个编号，或发生合并、更正。需要权威身份来源、域信息、映射与合并策略。姓名和生日可用于核查，但不能单独作为自动合并依据。

### Q4. DICOM 中 SOP Class 与 SOP Instance 有什么不同？

**参考答案：**Class 表示对象类型，Instance 表示某个对象实例。Study、Series 与 Instance 也各有身份。去重和引用不能用文件名替代这些身份，更不能把 SOP Instance UID 当患者 ID。

### Q5. RTSTRUCT、RTPLAN、RTDOSE 怎么理解？

**参考答案：**分别学习结构/轮廓、计划和剂量数据。导入时关注对象引用、空间关联和单位，而不是收到三个文件就认为计划完整。具体引用具有条件，不能说所有计划都必须引用同一种结构集，或所有剂量都固定一对一对应计划。

### Q6. C-ECHO 成功为何 C-STORE 仍可能失败？

**参考答案：**连接与验证服务可响应，不代表支持拟传送的对象类型和编码。继续检查关联协商、SOP Class、Transfer Syntax、端点/AE 配置及具体拒绝状态。即使存储成功，还要分开检查依赖完整性与业务处理状态。

### Q7. HL7 v2 的消息 ID 和患者 ID 在哪里？

**参考答案：**消息控制 ID 是 MSH-10，患者标识通常看 PID-3 及其中的域等组件。ACK 的 MSA-2 对应原消息 ID，ACK 自己的 MSH-10 标识 ACK。就诊/医嘱等还有各自业务身份，不能混用。

### Q8. 收到 ACK 是不是就可以宣布流程完成？

**参考答案：**先确认模式和代码。增强模式的接收确认与应用确认不同，CA 不是应用处理完成；AA 也不能代表后续治疗等工作流都已执行。要说明确认覆盖的阶段及后续失败如何反馈。

### Q9. FHIR 的 id 与 identifier 为什么分开？

**参考答案：**id 用于某服务器某资源类型的地址，identifier 表达业务身份及标识域。例如 Patient/patient-001 与医院的病历号 P0001 不同。跨系统匹配不能只比资源 id，也不能只比没有 system 的编号值。

### Q10. 什么是 Profile？为什么还要 CapabilityStatement？

**参考答案：**Profile 规定资源在特定场景的约束，能力声明描述实现支持的接口能力。两者分别帮助回答“数据必须怎样表达”和“这个端点能做什么”。基础资源有效、声明 meta.profile 与通过完整验证是不同事情。

### Q11. transaction 与 batch 有什么不同？

**参考答案：**transaction 整体成功或失败；batch 各 entry 独立处理，可以部分失败。batch 外层 200 时仍要逐项检查。FHIR 事务也不自动让服务器外部副作用参与同一个原子事务。

### Q12. 医疗标准是不是已经解决了权限和安全？

**参考答案：**标准提供信息交换的结构和相关机制，安全仍需要实现认证、授权、传输保护、审计和数据处理规则。FHIR JSON、MLLP 或一个 DICOM 端口本身不能证明已经具备这些控制。

以上定义的精确来源、版本与例外见[来源文档](../05-官方来源与事实边界.md)，面试时优先讲关键区别，不必背所有例外。

## 3. 场景问答：用工程能力拉开差距

### Q13. 外部消息重试后，出现两条患者记录

**参考答案：**先建立消息和业务时间线：是否第一次提交成功而 ACK 丢失？重发是否沿用消息 ID？来源域是否一致？再查看患者匹配和事务边界。设计上可用持久 Inbox 和唯一约束处理同消息竞争，但发送方换 ID 后，仍要靠业务身份规则避免同一意图重复产生效果。身份歧义隔离核查。修复需要覆盖丢 ACK、并发重发和重启恢复。

**不要答：**“加个 Redis 锁就好了。”锁不能替代持久身份和业务规则。

### Q14. 新更新先到，旧消息后到，患者数据被覆盖

**参考答案：**确认字段的权威来源、事件类型和业务版本契约，区分消息时间、接收时间与业务生效时间。存在可靠版本时拒绝旧版本倒退；没有时按约定顺序/补查权威状态/人工核查处理，不能假造序号或用本机时间判断一切。回归包含跨源、同时间戳、更正与重放。

### Q15. DICOM 接收成功，但轮廓叠加位置不对

**参考答案：**保留输入对象、版本和脱敏身份信息，检查引用的检查/序列/实例、Frame of Reference、影像位置/方向/间距及必要的坐标变换。确认单位、配准和显示转换是否一致。在测试环境用受控样本复现，不能靠拖动轮廓“修正”生产数据，也不能因矩阵尺寸一样就判断空间一致。

### Q16. FHIR 创建超时，客户端应该直接重试吗？

**参考答案：**超时代表结果未知，可能服务端已提交。先确认服务支持的条件创建或查询机制、业务标识和重试契约。查询后还要处理零条、多条、索引延迟和并发。不假设每台服务器支持自定义幂等头。失败原因和决策要可追溯。

### Q17. 两个人同时改同一个 FHIR 资源

**参考答案：**确认服务支持的版本策略，读取资源及 ETag，更新带 If-Match。冲突时重新获取并提示用户处理差异，不静默覆盖。412 和业务拒绝要分别呈现；不能无条件读最新版本后自动覆盖。涉及多资源还要确认事务支持与业务不变量。

### Q18. 医院升级后，只有一部分消息失败

**参考答案：**比较升级前后版本、实施规范、必填项、代码表、Z 段、字符集、空值和时间格式。选成功/失败脱敏样本控制变量，确认是传输、解析、约束、身份匹配还是业务规则失败。修复保持范围清晰，用历史样本、非法输入和重放验证，记录影响范围、根因与交付证据。

**可关联经历：**旧接口迁移体现契约与兼容性意识；退款并发体现锁序、事务与持久幂等；配置管理体现权限与审计。只说明工程方法的可迁移性，不声称这些项目就是临床系统集成经验。

## 4. 三段英文口述

**标准认知，约 30 秒：**

> DICOM handles medical imaging and related objects, including radiotherapy data. HL7 is a family of healthcare interoperability standards. HL7 v2 commonly uses event-driven messages, while FHIR organizes information as resources. For an integration, I would first confirm the versions, supported capabilities and implementation rules, then verify identity mapping, acknowledgements and failure recovery.

**能力边界：**

> I have studied the fundamentals, but I have not integrated these standards in a production clinical system. My Java background gives me a foundation in transactions, concurrency and API reliability. I would work with domain and quality specialists to validate clinical meanings and workflow requirements.

**故障调查：**

> I would separate transport success from application processing and workflow completion. I would collect the software versions, correlation identifiers and authorized test evidence, reproduce the failure, and check identity mapping and the interface contract. The fix should include regression tests for retries, duplicates and unexpected ordering.

## 5. 动手练习：不依赖真实患者或生产系统

这些是待完成任务。当前交付是学习文档，没有代你完成代码实验或标准一致性认证。可先做纸面版，之后用 Java 或 C# 和本地数据库实现。

### 练习 A：画一张接口契约表，约 30 分钟

为“HIS 向教学 OIS 同步患者信息”填写：权威系统、标识域、版本、事件、字段映射、必填/空值规则、确认模式、重试、错误队列、审计、访问权限与验收样本。

**验收：**同一个 P0001 分别来自 HOSP_A、HOSP_B 时不错误合并；能指出哪些业务规则需要领域人员确认。没有确定依据的格子标为待确认，不靠假设填满。

### 练习 B：读 HL7 消息与模拟重复处理，约 60–90 分钟

使用第 02 章消息，先人工定位 MSH-10、PID-3、版本与事件。编码版可使用成熟 v2 解析库；学习简化解析器只能声称支持这个示例，不能声称支持完整标准。

在本地设计 Inbox：`source / messageId / payloadFingerprint / processingState / result`，数据库约束去重作用域。业务更新与处理状态按设计在事务中保存；接收确认与应用结果分开处理。

| 输入/故障 | 预期证据 |
|---|---|
| 同一消息两次、并发两次 | 只有一次预期业务效果，并能关联已有结果 |
| 数据提交后模拟 ACK 丢失 | 重发不会再增加业务效果 |
| 同去重键换载荷 | 产生冲突记录，不覆盖原始证据 |
| 不同机构同消息 ID | 不被错误当作同一次发送 |
| 处理前/事务中重启 | 可以恢复或重试，状态与数据不互相矛盾 |

**验收：**输出输入、时间线、处理记录和业务效果次数。内存 HashSet 去重不能证明重启后可靠。

### 练习 C：FHIR 资源阅读与响应判断，约 45 分钟

用第 03 章 Patient JSON，分别写出资源地址、业务标识、资源版本。再手写一个 `searchset` 结果草图，并列出零命中、多命中、带 next 的处理。

准备一个 batch-response，包含一条 `201 Created` 和一条 `400 Bad Request`；说明哪些操作成功、失败项能否重试、外层 200 为何不够。最后用版本 7 读取、版本 8 被他人更新、If-Match 7 提交的时间线解释冲突。

**验收：**不会把 id 当 MRN；不会把 batch 当事务；不会无条件覆盖版本 8。如使用本地 FHIR 服务，记录实际软件和能力声明，不默认所有能力可用。

### 练习 D：DICOM 引用图，约 45 分钟

先做不依赖影像文件的元数据练习：虚构 image-A、struct-A、plan-A、dose-A 四个对象和引用关系。分别模拟依赖缺失、同 UID 输入冲突、患者域冲突、Frame of Reference 不匹配。

**验收：**能分类为重复、待依赖、冲突或需进一步校验；不把“对象都存在”当空间/临床验证通过。这个实验只能证明你理解引用检查，不能证明已实现 DICOM 网络协议。若进一步读取文件，用合成或经过授权的公开测试对象及成熟库，记录来源和限制。

### 练习 E：一页 RCA，约 30 分钟

题目：“教学接收端在提交成功后、发送 ACK 前重启，发送方重试，产生重复业务效果。”

写清：现象与影响；提交/ACK 时间线；可证伪假设；缺少持久去重或事务边界的证据；修复方案；丢 ACK、并发、重启等回归；剩余限制。若未编码复现，标题写“RCA 设计演练”，不写“已定位生产根因”。

## 6. 30 分钟模拟与评分

5 分钟讲系统地图与三类标准；10 分钟抽基础题；10 分钟抽两个故障题；5 分钟英文与反问。每项 0–2 分：概念准确、身份区分、成功阶段区分、故障证据、版本/能力、验证边界、经历真实性。总分 14；低于 10 时优先补最弱两项，评分用于自练，不预测录用。

可反问：“团队主要维护哪类外部接口？”“具体使用哪些标准版本和实施指南？”“客户接口问题的复现、支持与质量协作怎样分工？”“新人需要读哪些接口和领域资料？”

## 7. 面试前十分钟速记

- **系统：**OIS 管肿瘤记录与工作流，TPS 做计划相关工作，PACS 管影像归档通信。
- **身份：**患者号带域；消息 ID 不等于患者 ID；FHIR id 不等于 identifier；DICOM Class 不等于 Instance。
- **成功：**网络通、数据收到、持久化、应用处理、工作流完成分开讲。
- **DICOM：**先能力协商，再对象身份、引用和空间；C-MOVE/C-GET 关联使用不同。
- **HL7 v2：**MSH-10、PID-3、MSA-2；ACK 模式与边界；重复/乱序/空值/字符集。
- **FHIR：**R4 口径、Resource/Reference、Profile、CapabilityStatement、searchset 分页、batch 与 transaction、ETag。
- **调查：**影响 → 证据 → 复现 → 契约/身份/状态 → 修复 → 回归与可追溯交付。
- **经历：**学习、设计、亲手实现、生产经验分别说。
