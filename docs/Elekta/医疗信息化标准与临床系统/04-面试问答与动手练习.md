# 04｜医学小白怎样把知识讲成软件开发面试回答

这里是按 JD 设计的练习题，不是已核实的医科达真题。先练“能讲清楚”，再补技术细节。故事与处理方案均为教学例子；产品和标准依据见前面三章。

## 一、被问“你了解医疗行业吗”，怎样开场

### 30 秒简洁版

> 我之前主要做 Java 业务开发，最近围绕医科达的软件岗位学习了**肿瘤信息系统和医疗数据交换**。我理解 **MOSAIQ** 主要在**肿瘤信息和工作流管理**中发挥作用，TPS 支持**治疗计划**，PACS **管理影像**。DICOM 主要用于**医学影像及相关数据交换**，HL7 v2 常用于**医疗业务消息**，FHIR 用**标准资源**组织和交换医疗信息。我目前没有生产医疗系统集成经验，但能结合已有接口开发经验理解身份匹配、状态、重试和数据一致性问题。

### 60 秒带例子版

> 我用一个**患者从登记**、**影像检查**、**计划准备**到**预约和执行记录**的流程来学习。比如**患者资料**在医院系统**更新**后，可以通过 **HL7 v2 消息通知**其他系统；**影像及放疗相关对象**可以用 **DICOM** 交换；另一个应用也可以通过 **FHIR 资源接口**获取 **Patient** 或**预约信息**。我理解接入医疗系统不能只看接口返回成功，还要看是不是正确患者、数据是否关联正确、消息有没有重复，以及业务处于什么状态。我以前的接口兼容、事务和故障排查经验有可以迁移的部分，具体临床含义和质量流程还需要跟团队学习。

这两段可以按你的语言习惯调整。不要一开口就罗列 MSH、SOP、MLLP、ETag；先让面试官知道你理解业务对象和工程问题。



### 可选的业务规则模拟｜临床工作流：资料接收、审核、预约、执行分别记录

```csharp
// 只是教学状态快照，不定义真实系统的审批规则。
bool planReceived = true;
bool planApproved = false;
bool appointmentBooked = true;
bool treatmentCompleted = false;

Console.WriteLine($"计划已接收：{planReceived}");
Console.WriteLine($"计划已批准：{planApproved}");
Console.WriteLine($"预约已安排：{appointmentBooked}");
Console.WriteLine($"治疗已完成：{treatmentCompleted}");
```

**输出：**

```text
计划已接收：True
计划已批准：False
预约已安排：True
治疗已完成：False
```

四个 bool 表达四种不同事实。计划接收不自动改变批准状态，预约存在也不自动改变治疗完成状态。

本例用 bool 让概念直观；真正系统可能用状态机、记录表及角色权限表达，并验证合法状态变化。不要据此认为任何状态组合都合法。

这也解释了 API 返回成功必须说明“哪一步成功”：接收接口的成功不能代替临床审批或实际执行。

**改一处观察：**只把 planApproved 改为 true，观察 treatmentCompleted 仍然是 False。

## 二、六个基础问题，用例子把概念说清楚

### Q1. 医科达的 MOSAIQ 做什么？

**先理解：**治疗涉及多个角色和多项信息。医生关心患者情况，相关人员关心计划和审核，工作人员关心排程，后续还要查看记录。需要软件把这些资料和流程联系起来。

**例子：**张明已经登记，计划资料正在准备，明天有预约。工作人员需要知道这些信息分别处于什么状态，不能到几个地方人工寻找后再猜进度。

**回答：**

> 我了解到 MOSAIQ 是面向**肿瘤信息和工作流管理**的产品，可以**支持**相关人员**围绕患者资料和临床工作流协作**。它与治疗计划系统职责不同，也可能集成。具体到这个岗位，我希望了解团队负责的是患者信息、工作流、外部接口还是其他模块。

**重点：**能说出信息和工作流，不把 MOSAIQ 简单说成影像库或剂量计算程序。

### Q2. DICOM、HL7 v2、FHIR 分别怎么解释？

**用同一位患者回答：**

> 张明的 **CT 影像**要让其他软件看懂**患者身份、检查和空间等信息**，可以涉及 **DICOM**；医院系统**更新张明的资料后发业务通知**，可以涉及 **HL7 v2**；应用通过**约定的资源接口**查询张明的 Patient 信息，可以涉及 **FHIR**。**FHIR 也属于 HL7 标准家族**，三者可以在医院环境中共存。

**重点：**说用途并给例子。不要说“DICOM 就是 JPG”“FHIR 就是所有 JSON 接口”。

### Q3. 为什么医疗信息交换需要标准？

**例子：**一个系统用 `patientNo`，另一个用 `person_code`。即使改对字段名，还要处理编号所属机构、姓名结构、状态含义、结果单位等差异。

**回答：**

> 标准给**不同厂商**一个**共同的信息模型和交流基础**，**降低每次对接都从零解释数据的成本**。但实际项目仍要确认版本、字段约定、支持能力和业务含义。采用相同标准不代表接上网络就一定完全互通。

**重点：**“互操作”就是不同系统能交换信息并正确使用信息。它既包含传输，也包含对含义的共同理解。

### Q4. 为什么医疗影像不直接用普通图片传输？

**例子：**收到一张叫 zhangming.png 的图，无法可靠知道是哪个张明、哪次检查、在身体中的哪一层、方向和尺寸如何。

**回答：**

> 医学影像需要**图像之外的身份**、**检查**和**空间信息**。DICOM 为医学影像及相关数据提供**标准表达和交换方式**。例如轮廓需要与正确影像对应，不能只根据文件名或姓名叠加。

**重点：**格式读得开不等于数据能正确用于相关工作流。

### Q5. FHIR 的资源到底是什么？

**例子：**Patient 表达张明的患者信息，Appointment 表达他某个时间的预约。预约引用参与者，两者联系起来，但不是同一个对象。

**回答：**

> 资源可以理解为有标准含义的数据对象，例如 **Patient、Appointment 和 Observation**。不同资源通过引用联系。我的 REST 和 JSON 经验能帮助入门，但还需要学习具体资源规则，以及接口的能力和约束。

**重点：**可以类比 Java 模型，不能假定每个资源对应固定的一张表。

### Q6. 为什么“患者号”和“消息号”不能混用？

**例子：**张明的患者号是 A 医院的 P0001，资料更新消息号是 MSG-100。明天再次更新，患者号通常仍然指向张明，新的消息则有自己的编号。

**回答：**

> 患者业务编号说明涉及谁，消息编号说明哪次消息，FHIR 资源 id 说明服务中的哪份资源。它们分别用于身份关联、消息追踪和资源寻址。混用可能造成重复记录或错误更新。

**重点：**患者编号也要结合所属标识体系；同名、同编号都不能自动证明是同一个人。

## 三、三个软件场景题，按步骤讲而不是堆术语

### 场景 A：患者资料同步超时，重试后出现两条记录

**发生了什么：**HIS 发消息，接收方已经处理并保存记录，但回给 HIS 的确认丢了。HIS 重发，接收方把同一次业务又处理了一遍。

**先判断什么：**超时只说明发送方没等到回复。它不能证明接收方没有处理。因此先建立“发送、接收、提交、回复、重试”的时间线。

**具体怎样查：**

1. 查同一患者的两条记录是否确实由这次同步产生，排除原本就有重复资料。
2. 用消息编号和来源机构关联日志，比较第一次发送与重试的内容。
3. 查看第一次数据库提交是否成功，重复处理判断是否保存、是否能跨服务重启保留。
4. 如果有并发，检查两个处理线程是否都认为“没处理过”，以及数据库约束和事务是否生效。

**修复思路：**按约定作用域持久保存消息身份和处理结果，重复请求识别为同一次发送；业务身份规则帮助避免同一意图重复产生效果。并发由数据库约束和事务等机制配合处理。具体实现取决于接口契约。

**怎样验证：**正常一次；同一消息两次；并发两次；提交成功后回复丢失；服务重启后重试。看最终业务效果次数和状态，不只看返回码。

**面试口述：**

> 我会先确认是不是第一次处理成功但回复丢失，超时本身不代表失败。然后按来源和消息编号追踪，检查持久去重与业务事务。修复后会覆盖重复、并发、回复丢失和重启后的重试，确认不会再产生额外业务效果。

### 场景 B：系统收到计划资料，但页面提示不能使用

**发生了什么：**教学接收端保存了计划文件，但是计划关联的一份资料尚未到齐，或者患者、版本、状态没有满足要求。

**先判断什么：**“收到文件”只是接收阶段，不能把问题直接归为网络故障，也不能直接设置成“可使用”。

**具体怎样查：**

1. 明确错误现象：是传输失败、读不懂文件、找不到关联资料，还是业务规则不允许。
2. 查看输入和解析结果，确认对象对应正确患者及相关检查/计划上下文。
3. 查看引用资料是否存在、是否是预期版本，比较一个成功样本与失败样本。
4. 若涉及几何/临床语义，按既定规则并与领域人员一起核对，不自己猜“把状态改掉就好”。

**怎样验证：**准备资料齐全、资料缺失、错误关联、重复导入等测试场景；检查错误提示和处理状态是否与真实情况一致。

**面试口述：**

> 我会把数据**接收**、**解析**、**关联检查**和**业务处理**分开定位。比如文件保存成功但引用资料不齐，这时应展示明确的待处理原因。修复要有可复现输入和回归证据，不能只把界面提示隐藏或直接改成功状态。

### 场景 C：A 医院和 B 医院都传来了 P0001

**发生了什么：**A 医院的 P0001 是张明，B 医院的 P0001 是李华。程序只用编号匹配，错误地更新同一条记录。

**先判断什么：**这不是简单的重复发送，而是身份范围理解错误。两个系统使用相同编号，不一定表示同一患者。

**具体怎样查：**确认编号所属体系、发送来源、已有映射和身份主数据规则；找出哪些输入被错误关联及影响范围。

**修复思路：**按约定域理解业务编号，在明确身份映射下关联。冲突或歧义进入核查流程。误关联造成的历史数据影响需要单独评估，不能只改代码就认为所有旧数据自动恢复。

**怎样验证：**相同编号不同医院；相同姓名不同患者；同一患者多个编号；既有映射与新消息冲突。

**面试口述：**

> 我会先核对患者编号的标识域和权威来源，避免用裸编号或姓名自动关联。代码修复之外，还要评估已产生的错误关联及恢复方案，并补充跨机构编号碰撞等回归用例。

## 四、三个补充问题：体现软件开发岗位的判断

### Q7. 医疗软件和普通业务软件有什么不同关注点？

> 共通的部分是**功能正确、可维护和可靠交付**。医疗软件还要理解**错误会影响哪一步工作流**，**重视患者和数据关联、权限、状态以及变更证据**。例如预约成功不能等同于治疗完成。我会按团队质量流程做需求确认、评审、测试和发布，并向领域人员学习临床语义。

“变更证据”可以具体理解成：哪条需求或缺陷、哪个提交、怎样测试、什么版本交付。不要仅说“医疗软件更严格”然后没有例子。

### Q8. 接口数据到了，页面没有显示，你怎么查？

> 我会**沿数据链路分段检查**：是否接收到、是否解析并保存、是否关联正确患者、查询是否过滤掉、当前用户是否有权限、页面是否正确处理状态。这样区分数据缺失和展示问题，复现后再做范围清晰的修复。

举例：张明的数据在数据库里，但被关联到错误患者，或被状态筛选排除。查到数据库有行，并不证明页面问题只是缓存。

### Q9. 没有医疗行业经验，为什么觉得能够胜任？

> 我有业务接口、关系数据库和问题排查的基础，能够从数据契约、状态和失败路径理解系统。我通过患者流程学习了医疗系统分工和三类标准的用途。已有工程能力可以迁移，临床业务和质量流程需要继续学；入职后我会先阅读模块文档和真实缺陷案例，在团队指导下完成小范围需求与修复。

这段回答用具体基础和学习方法支撑，不把“短期看了资料”说成“已熟悉全部医疗协议”。

## 五、怎样联系你的真实项目经验

| 已有经历 | 可以迁移的工程思路 | 用医疗例子说明 |
|---|---|---|
| 旧接口迁移与兼容 | 对比请求/响应契约、状态与异常行为 | 医院接口升级后旧消息还能否正确解释 |
| 退款并发与幂等 | 区分锁、事务、持久状态与重复效果 | 消息重试不能创建重复业务效果 |
| 配置管理和权限 | 谁能改、能改什么、变化如何追踪 | 不同角色对数据有不同操作权限 |
| SQL 与故障定位 | 沿链路定位、控制变量比较输入 | 数据收到但页面不显示时逐段检查 |

如果被追问具体实现，讲自己项目中真实使用的方法，再说“医疗接口里的具体规则要按标准和业务确认”。已有经历证明软件工程基础，不能替代患者匹配和临床规则知识。

## 六、20 分钟纸面练习，答案就在下面

### 练习 1：给软件分工，约 5 分钟

把“影像归档”“治疗计划”“肿瘤患者信息与工作流”分别放到 PACS、TPS、OIS 中。

**答案：**PACS 对应影像归档和通信；TPS 对应治疗计划；OIS 对应肿瘤信息与工作流。系统可能集成，分工不意味着数据完全隔离。

### 练习 2：给数据找用途，约 5 分钟

张明的影像及相关数据要传给另一软件；HIS 要通知患者资料更新；一个应用要通过资源 API 查询患者。分别用哪种标准的例子解释？

**答案：**DICOM、HL7 v2、FHIR REST。它们是教学中的典型用法，不是三种标准全部能力的互斥划分。

### 练习 3：找出一句错误描述，约 5 分钟

“医院发消息超时了，所以接收方一定没处理。我直接重发；收到 ACK 后就标记治疗已完成。”

**答案：**超时可能发生在提交之后；重发要按约定处理重复；ACK 的含义取决于确认范围；消息处理成功不证明治疗实际完成。这里混淆了通信、应用处理和临床业务状态。

### 练习 4：用自己的经历连接，约 5 分钟

填这两句：“我做过的相关工程问题是____；面对医疗系统中的____问题，我会先____。”

**参考：**“我做过接口兼容和异常处理；面对医院升级后部分消息处理失败，我会先比较版本、字段契约和成功/失败样本，再分段复现定位。”请用自己的真实经历替换。

完成这些练习属于基础学习。需要写代码的完整接口实验在[进阶版](进阶参考/04-面试问答与动手练习.md)，不作为这轮速学的前置任务。

## 七、两段简单英文，先能清楚表达

**介绍学习情况：**

> I have a Java development background. I have studied the basics of healthcare systems and data exchange. DICOM supports medical imaging and related data. HL7 v2 is commonly used for healthcare messages. FHIR organizes information as resources. I have not worked on a production clinical integration yet.

中文意思：我有 Java 开发背景，学习了医疗系统和数据交换基础，理解三类标准的用途，目前没有生产医疗集成经验。

**讲一个工程重点：**

> A timeout does not always mean the operation failed. The server may have saved the data before the response was lost. I would check the message history and make sure a retry does not create a duplicate effect.

中文意思：超时不一定说明操作失败，可能数据已经保存而回复丢失；要查消息时间线并防止重试产生重复效果。

## 八、面试前最后一页

**业务主线：**患者登记 → 影像资料 → 计划准备与审核 → 相应排程与执行记录。每一步的数据和状态要分清。

**系统分工：**PACS 管影像；TPS 支持计划；OIS/MOSAIQ 组织肿瘤信息与工作流。

**三个标准：**DICOM 讲影像及相关对象；HL7 v2 讲业务消息；FHIR 讲标准资源与交换。用张明的故事举例。

**三个工程重点：**数据属于谁？关联的是哪份资料？接口成功到了哪一步？

**三个故障例子：**回复丢失造成重发；引用资料缺失导致不能处理；跨医院同编号造成身份冲突。

**回答结构：**先说现象 → 举例解释原因 → 说怎样查 → 说如何验证。不要一口气堆缩写。

**反问可以选一句：**“团队负责 MOSAIQ 哪个模块？”“新人最需要了解哪些临床流程和外部接口？”“开发与质量团队怎样协作处理客户问题？”

标准与产品准确依据见[官方来源](05-官方来源与事实边界.md)。这份材料的目标是让你能解释基础、表现工程判断，再逐步学习具体实现。
