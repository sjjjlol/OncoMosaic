# 官方来源与事实边界

核验日期：2026-10-02。用于 Elekta 软件开发岗位面试准备。以下区分标准规定、产品公开事实与工程推导；不把通用标准能力推定为某个 MOSAIQ 版本已开放的接口。

## 1. 版本和来源使用方式

- **DICOM**：本次读取 NEMA DICOM 官方 `current` 页面，返回页眉为 **2026d**。`current` 会随发布变化；实际项目应固定标准版、设备软件版及厂商 DICOM Conformance Statement。参考 [DICOM 标准入口](https://dicom.nema.org/medical/dicom/current/output/chtml/part01/chapter_1.html)。
- **HL7 v2**：基础字段和 ACK 行为以 **v2.5.1** 学习；正文来自 HL7 Europe 官方域 `hl7.eu` 的标准展示。MLLP 的公开说明来自同域 **v2+ demo**，用于核对帧格式，不能冒充指定医院的已批准实施指南。参考 [HL7 Europe](https://hl7.eu/)、[v2.5.1 第 2 章](https://hl7.eu/HL7v2x/v251/std251/ch02.html)、[MLLP 说明](https://hl7.eu/refactored/transport01mllp.html)。
- **FHIR**：统一使用 **R4 4.0.1** 固定版本，便于示例一致；不声称 R4 是最新版本。R4 官方页明确为固定发布版本，具有 Normative/STU 混合状态。实际接口先查 `CapabilityStatement.fhirVersion`、资源/操作和实施指南。参考 [R4 REST API](https://hl7.org/fhir/R4/http.html)、[发布版本目录](https://hl7.org/fhir/directory.html)。

## 2. DICOM：已核验事实

### 标识与对象层级

常规复合对象学习模型为 Patient → Study → Series → SOP Instance；CT 一个 SOP Instance 可以是单帧或多帧，不能把实例机械理解为“一个切片”。Study Instance UID、Series Instance UID、SOP Instance UID 标识不同实体；Patient ID 并非这些 UID。SOP Class UID 标识对象类别，SOP Instance UID 标识对象实例。参考 [存储服务与信息模型](https://dicom.nema.org/medical/dicom/current/output/chtml/part04/chapter_B.html)、[Enhanced CT IOD](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_A.38.html)。

UID 要在 DICOM 标识空间中唯一，同一 UID 不能同时当 Study 和 Series 的标识；UID 不应解析出业务语义。不要从别人的 UID 任意追加后缀生成新 UID。UID 编码长度上限包含必要的 NULL 填充共 64 字符。参考 [PS3.5 第 9 章 UID](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/chapter_9.html)。

### 网络操作

| 服务 | 精确理解 | 易错边界 |
|---|---|---|
| C-STORE | SCU 向 SCP 传送对象实例 | 成功仅说明按存储服务语义完成；不自动表示永久归档、临床审批或可查询。存储持续时间和访问方式需看一致性声明。 |
| C-FIND | 按所协商信息模型和查询键查询 | 可连续返回多个 Pending，最终 Success 不带匹配 Identifier；不是任意 SQL。 |
| C-MOVE | 请求远端将匹配实例通过 C-STORE 发往目标 AE | C-STORE 使用**另一个 Association**，目标可与请求方不同；MOVE 不表示删除源对象。 |
| C-GET | 请求远端返回匹配实例，通过 C-STORE 子操作传送 | 使用**同一个 Association**；执行 C-STORE 时存储服务 SCU/SCP 角色反转。 |

来源：[Storage Service](https://dicom.nema.org/medical/dicom/current/output/chtml/part04/chapter_B.html)、[Query/Retrieve 概览](https://dicom.nema.org/medical/dicom/current/output/chtml/part04/chapter_C.html)。

DICOMweb 是 HTTP 家族协议上的 DICOM Web 服务。常见教学名称：QIDO-RS 查询、WADO-RS 检索、STOW-RS 存储；属于 Web 服务路径，不能把它们称为 C-FIND/C-GET/C-STORE 在 HTTP 上的同一报文。实际支持的资源、表示形式、传输语法和安全策略须查服务器能力与一致性声明。参考 [PS3.18 Scope](https://dicom.nema.org/medical/dicom/current/output/chtml/part18/chapter_1.html)、[Studies Service](https://dicom.nema.org/medical/dicom/current/output/chtml/part18/chapter_10.html)。

### 放疗对象与空间

- **RTSTRUCT**：传送结构、ROI 和相关引用；轮廓是患者坐标中的 `(x,y,z)` 三元组，单位 mm。ROI Number 是结构集内标识；轮廓通过 Referenced ROI Number 关联 ROI。不要直接把轮廓数值当像素索引。参考 [RT Structure Set IOD](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_A.19.html)、[Structure Set Module](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.8.8.5.html)、[ROI Contour Module](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.8.8.6.html)。
- **RTPLAN**：传送计划，可包含分次信息、外照射束或近距离治疗设置。`RT Plan Geometry=PATIENT` 时要求 Referenced Structure Set Sequence；`TREATMENT_DEVICE` 并不要求患者结构集。故“所有 RTPLAN 必定引用 RTSTRUCT”过度概括。参考 [RT Plan IOD](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_A.20.html)、[RT General Plan](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.8.8.9.html)。
- **RTDOSE**：可传送 2D/3D 剂量分布及 DVH。网格像素乘 `Dose Grid Scaling` 后才得到 `Dose Units` 指定单位的剂量；不能一概认定原始像素就是 Gy。Referenced RT Plan 的要求及基数随 Dose Summation Type 等条件而变，不是始终“一份剂量对应一份计划”。参考 [RT Dose IOD](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_A.18.html)、[RT Dose Module](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.8.8.3.html)。
- Image Position/Orientation、Pixel Spacing、Frame of Reference UID 是空间校验关键。BIPED 或未指定 Anatomical Orientation Type 时，患者坐标 x 向左、y 向后、z 向头；有 QUADRUPED 特例。剂量平面不必与 CT 平面一致；同一个患者或相同矩阵尺寸不足以证明可叠加。**工程推导**：导入须验证引用完整性、坐标映射和必要的配准，不能靠文件名或数组下标拼接。参考 [Image Plane Module](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.7.6.2.html)、[RT Dose Module](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.8.8.3.html)。

## 3. HL7 v2：已核验事实

ADT 是患者管理消息，需结合触发事件理解，如入院/更新/合并；ORM^O01 是通用医嘱消息学习入口，v2.5.1 已注明 ORM 保留用于向后兼容，并推荐 OMG/OML/OMI 等更具体消息，不能把所有版本、所有医嘱场景都限定为 ORM；ORU^R01 是观察结果非请求式发送场景，常见 OBR/OBX 组合。消息结构、字段用法、代码表、Z 段及 ACK 行为须按版本和双方接口协议核定。参考 [v2.5.1 患者管理](https://hl7.eu/HL7v2x/v251/std251/ch03.html)、[医嘱](https://hl7.eu/HL7v2x/v251/std251/ch04.html)、[观察报告](https://hl7.eu/HL7v2x/v251/std251/ch07.html)。

`MSH-10` 是该消息的 Message Control ID。ACK 的 **MSA-2 回显原消息 MSH-10**；ACK 自身 MSH-10 标识新生成的 ACK，不能直接把它当回显字段。参考 [第 2 章 §2.9、§2.15.8、§2.15.9.10](https://hl7.eu/HL7v2x/v251/std251/ch02.html)。

| ACK 模式 | 条件 | 理解 |
|---|---|---|
| Original | MSH-15、MSH-16 均缺省/空 | 按原始处理规则返回应用确认；AA/AE/AR 分别为应用接受/错误/拒绝。 |
| Enhanced | MSH-15 或 MSH-16 至少一个非空 | 区分接收确认与应用确认；MSH-15/16 的 AL、NE、ER、SU 决定何时要求返回。 |
| Enhanced 接收确认 | 按 MSH-15 要求 | CA/CE/CR；CA 表示接受并承担安全存储责任，不等于后续应用业务已处理完成。 |
| 应用确认 | 按 MSH-16 或原始模式规则 | AA/AE/AR；仍不能据此推断治疗已执行或临床结果已获批准。 |

来源：[HL7 v2.5.1 §2.9](https://hl7.eu/HL7v2x/v251/std251/ch02.html)、[HL7 Australia ACK 实施说明](https://hl7.org.au/archive/hl7v2wg/8-Acknowledgement_31588902.html)。**工程推导**：ACK 超时后的重发策略与幂等键须约定；TCP 收到字节、收到 CA、收到 AA 是不同层次的证据。

MLLP 帧形如 `0x0B + HL7内容 + 0x1C + 0x0D`；段结束通常是 CR。TCP 是字节流，因此一次 read 未必恰好是一条消息；帧解析须处理拆包与多帧连读。后一点属于 TCP/工程推导。MLLP 本身的帧格式不自动提供加密、认证或授权。参考 [HL7 v2+ MLLP demo（非医院实施指南）](https://hl7.eu/refactored/transport01mllp.html)。

## 4. FHIR R4：已核验事实

- **id 与 identifier**：`Resource.id` 在同一服务器、同一资源类型范围内唯一，用于 `Patient/123` 等 URL；跨服务器复制后可能不同。`identifier` 是业务标识，通常以 `system + value` 解释命名空间，如医院患者编号；并非每种资源都具有 identifier。业务身份匹配仍需识别发号机构、合并历史与数据质量。参考 [R4 Resource Identity](https://hl7.org/fhir/R4/resource.html#id)、[Identifier](https://hl7.org/fhir/R4/datatypes.html#Identifier)。
- **search**：标准搜索不是直接查询任意 JSON 字段；服务端声明支持的 SearchParameter。搜索响应使用 `Bundle.type=searchset`；结果可能分页，须处理 next 链接，且可含 include/outcome 条目，不能把每个 entry 都算作命中。参考 [R4 Search](https://hl7.org/fhir/R4/search.html)、[R4 REST Search](https://hl7.org/fhir/R4/http.html#search)、[Bundle](https://hl7.org/fhir/R4/bundle.html)。
- **Bundle**：是多资源的容器，类型决定语义。`transaction` 在支持该交互的服务器上全成或全败；`batch` 条目独立，不保证跨条目原子性。batch 外层 HTTP 200 仍可能有失败 entry，应逐项检查 response.status。二者向服务基址 POST，不是向 `/Bundle` 创建普通资源。参考 [R4 batch/transaction](https://hl7.org/fhir/R4/http.html#transaction)。
- **CapabilityStatement**：描述指定软件/部署的支持能力，如版本、资源、交互、搜索参数、操作等；并非所有 FHIR 服务器都实现所有资源、事务或条件操作。REST 能力通过 `[base]/metadata` 获取。参考 [CapabilityStatement](https://hl7.org/fhir/R4/capabilitystatement.html)、[REST API](https://hl7.org/fhir/R4/http.html#capabilities)。
- **Profile**：用 StructureDefinition 等机制对基础资源作约束或扩展，限定基数、术语绑定、切片等；“符合基础 Patient 结构”不足以保证满足指定实施指南。声明 `meta.profile` 也不等于已经通过服务器验证。参考 [R4 Profiling](https://hl7.org/fhir/R4/profiling.html)。
- **OperationOutcome**：表达处理结果、校验问题或错误细节；可能出现在失败响应或其它允许场景中。不是每个 4xx/5xx 都必然附它，底层代理/框架也可能生成非 FHIR 错误；应同时检查 HTTP 状态、Content-Type 和 body。参考 [OperationOutcome](https://hl7.org/fhir/R4/operationoutcome.html)、[HTTP 错误说明](https://hl7.org/fhir/R4/http.html#status)。
- **ETag / If-Match**：在支持版本控制的服务器上使用弱 ETag，如 `W/"23"`，版本应与 meta.versionId 对应。更新请求携带 `If-Match` 可避免覆盖他人更新；版本不匹配返回 **412 Precondition Failed**。服务器版本能力与策略须先确认，版本号不保证为可递增整数。参考 [Managing Resource Contention](https://hl7.org/fhir/R4/http.html#concurrency)。
- **安全**：FHIR 是交换规范，不因“采用 FHIR”就自动完成认证、授权、审计、加密或同意管理。实际系统须落实 HTTPS、身份、访问控制、审计及组织政策；若使用 SMART/OAuth 等，也需核对服务器实际实现。参考 [R4 Security](https://hl7.org/fhir/R4/security.html)、[R4 REST API 安全边界](https://hl7.org/fhir/R4/http.html)。

## 5. Elekta 产品边界与面试表达

Elekta 官方产品页面确认：MOSAIQ 用于肿瘤工作流/信息管理；Monaco 属于治疗计划系统 TPS。官方案例明确两者集成，不能将 MOSAIQ 和 Monaco 当作同一个系统。参考 [Elekta Oncology Care](https://www.elekta.com/products/oncology-informatics/elekta-one/oncology-care/)、[Monaco 与 MOSAIQ 集成案例](https://www.elekta.com/focus/transition-to-monaco-completes-elekta-environment-and-allows-huge-time-savings-at-genesiscare/)。

Elekta 互操作产品页提及 HL7、EHR 集成和开放标准；这**不足以证明招聘团队正在使用某个 HL7 v2 消息组合、FHIR R4 服务、具体认证方式或所有 DICOM RT 对象**。可在面试中说：

> 我理解 OIS 与 TPS 的职责区别，并按患者身份、消息确认、DICOM 引用与坐标、FHIR 能力及版本进行接口设计。我会先查看具体版本的一致性声明与接口实施指南，再确定映射、幂等、验证和故障恢复方案。

这段是建议的个人表述，不是产品资料原文。产品能力依据：[Elekta Interoperability](https://www.elekta.com/products/oncology-informatics/interoperability/)。
