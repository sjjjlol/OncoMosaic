# 02｜HL7 v2：医院系统之间怎样发“业务通知”

继续张明的故事。本章不要求记住所有字段，先理解“发消息通知变化”和“可靠处理消息”这两件事。

## 一、张明登记了，为什么另一个系统还不知道

A 医院的 HIS 保存了张明的资料，但肿瘤科使用的是另一套系统。它们可能有各自的数据库。HIS 新增一条记录，不代表另一套系统的数据库自动多一条记录。

如果靠工作人员复制姓名、编号，容易重复录入或输入错误。软件可以改成：HIS 发送一条消息，告诉接收方“新增了这位患者，这是相关资料”。接收方按约定处理，创建或关联自己的记录。

问题是：这条消息应该怎么写？用 `patientNo` 还是 `patientId`？患者编号有没有所属医院？这次是新增还是修改？接收方怎样知道消息来自谁？双方需要共同约定。

**HL7 v2 就是医疗系统交换消息的一种标准。**它提供消息类型、结构和字段等规则，让不同厂商有共同的交流基础。医院仍要约定实际使用哪些消息和字段。

## 二、先用中文读懂一条消息

先不看协议文本。想象收到下面这张“业务通知单”：

```text
发送方：A 医院的 HIS
接收方：教学肿瘤信息系统
事件：患者信息更新了
消息编号：MSG-100
患者编号：P0001
编号所属医院：HOSP_A
患者姓名：张明
```

你已经能读出三类内容：**谁和谁沟通、发生了什么、涉及哪个患者。**HL7 v2 消息也是要把这些内容表达清楚。

这里的“事件”很好理解：系统中的某件事发生了，需要通知其他系统。登记、就诊、信息更新、检查结果产生，都可能引发消息。它和你熟悉的订单状态变更通知在工程思路上有相似之处。

## 三、再看真正的消息长什么样

以下是 v2.5.1 的简化教学示例，使用患者信息更新事件。姓名用英文测试值，避免字符集细节打断学习。它不是可以直接投放到医院接口的完整样本。

```text
MSH|^~\&|HIS|HOSP_A|OIS|ONC_A|20261007090000+0800||ADT^A08^ADT_A01|MSG-100|T|2.5.1
EVN|A08|20261007090000+0800
PID|1||P0001^^^HOSP_A^MR||ZHANG^MING
PV1|1|O
```

不用逐格数位置，先抓住这几个片段：

| 看到什么 | 中文理解 | 对应通知单 |
|---|---|---|
| `MSH` | 消息头，相当于信封上的发送和接收信息 | 谁发给谁、消息类型、消息编号 |
| `HIS`、`HOSP_A` | 发送应用和发送机构 | A 医院的 HIS |
| `ADT^A08` | 患者信息更新事件 | “资料更新了” |
| `MSG-100` | 这条消息的控制编号 | 消息编号 |
| `PID` | 患者身份相关信息段 | 哪位患者 |
| `P0001^^^HOSP_A^MR` | 示例中的病历号及其签发机构等 | A 医院的 P0001 |
| `ZHANG^MING` | 示例姓名的组件表达 | 张明 |
| `PV1` | 就诊相关信息段 | 患者处于什么就诊上下文 |

`|` 用于分隔字段，`^` 用于分隔字段内部组件。你可以把一段消息想象成“按标准排列的一行表格”。这只是阅读类比；完整解析还涉及重复、转义和编码等规则。

**本章只要求读懂三件事：消息来自谁、什么事件、哪个患者。**ADT^A08 的消息结构使用 ADT_A01，这是标准的结构命名，不需要为入门专门背诵。



### C# 协议 API｜用 nHapi 解析消息并读取字段

依赖 nHapi 3.2.4，使用 NHapi.Base.Parser 与 NHapi.Model.V251.Message。

```csharp
string text = @"MSH|^~\&|HIS|HOSP_A|OIS|ONC_A|20261007090000+0800||ADT^A08^ADT_A01|MSG-100|T|2.5.1"
    + "\rEVN|A08|20261007090000+0800"
    + "\rPID|1||P0001^^^HOSP_A^MR||ZHANG^MING"
    + "\rPV1|1|O\r";

var parser = new PipeParser();
var message = (ADT_A01)parser.Parse(text);
var identifier = message.PID.GetPatientIdentifierList(0);
Console.WriteLine($"消息号：{message.MSH.MessageControlID.Value}");
Console.WriteLine($"患者号：{identifier.IDNumber.Value}");
Console.WriteLine($"患者号签发机构：{identifier.AssigningAuthority.NamespaceID.Value}");
```

Parse 把消息变成对象，PID 和 MSH 提供段访问，字段 Value 给出实际值。A08 复用 ADT_A01 结构。输出为消息号 MSG-100、患者号 P0001、签发机构 HOSP_A。库提供模型访问，你无需靠 split 数组下标写业务代码。

还可修改属性后调用 Encode，完整例子见[协议 API 实战](07-CSharp医学协议API实战.md)。


## 四、“患者”“一次就诊”“一项医嘱”“一个结果”分别是什么

### 1. 患者是人，就诊是某次业务过程

张明这个人只有一个当前讨论的身份，但他可能周一看门诊，过一段时间又住院。同一个患者会有不同的就诊上下文。

对程序来说，`patientId` 和 `encounterId` 不是一回事。只知道“这个结果属于张明”，可能仍然不够，还需要知道相关就诊或申请。

### 2. 医嘱可以理解为需要执行的医疗服务要求

例如医生安排“做一次相关检查”，这涉及服务请求。入门先把“医嘱”理解为由有权限的临床人员提出的医疗服务要求；它的实际内容也可以包括其他类型的服务。

它不是检查已经完成的证明。你可以类比“创建了任务”和“任务执行完成”的区别。

### 3. 结果是执行之后形成的信息

安排检查是一个动作，产生检查结果是另一个动作。系统需要让申请和结果对应正确。

传统 v2 中常会遇到 ADT（患者管理）、医嘱类消息和 ORU（观察结果报告）等。先理解业务区别，再查消息类型。医嘱消息不必现在背 ORM、OMG、OML、OMI 的差异。

## 五、最关键的例子：系统回应“收到了”，是什么意思

### 1. ACK 是确认响应

**ACK** 可以先记作“接收方发回的确认消息”。发送方发出 MSG-100，接收方回应，并指出它确认的是 MSG-100。这样发送方能把回复和原消息对应起来。

类比寄件：寄件单有编号，签收信息要指向那张寄件单。否则多条消息同时发送时，你不知道哪一条得到回复。

### 2. 收到与处理完成可能不是同一阶段

接收方可能先把消息保存，稍后由后台任务处理。也可能校验失败：患者标识缺失，或资料与已有记录有冲突。

HL7 v2 的确认有不同模式和代码，具体确认范围要按接口约定。入门只抓住这个问题：**对方的确认是在说“消息已接收”，还是“相应应用处理已接受”？**即使应用处理成功，也不能据此推出患者已经接受治疗。

进阶中的 AA、CA 和字段编号，是为了精确区分这些情况。现在先掌握“成功有阶段”。

### 3. 确认丢失为什么会导致重复

看这条时间线：

```text
09:00:00 HIS 发送 MSG-100
09:00:01 接收方处理成功，并保存了结果
09:00:02 接收方发回 ACK，但连接中断，HIS 没收到
09:00:05 HIS 超时，以为可能没送到，于是重新发送
```

对 HIS 来说结果未知；对接收方来说第一次已经成功。如果接收方每收到一次就新增一条记录，重发就可能产生重复效果。

所以开发者需要 **幂等**：同一次业务意图被重试时，不重复产生额外效果。一个常用工程思路是保存消息标识和处理结果，识别已处理消息；并发时配合数据库约束和事务。消息的来源也要参与身份判断，因为其他医院也可能发一个叫 MSG-100 的消息。

这是通用设计思路，具体去重规则要按接口约定。发送方换消息编号重新表达同一个业务时，还需要业务层规则，不能只看消息 ID。



### 可选的业务规则模拟｜HL7 重发：同一条通知收到两次，只模拟处理一次

```csharp
var processedMessages = new HashSet<(string Source, string MessageId)>();

void Receive(string source, string messageId)
{
    // Add：首次加入返回 true，已存在返回 false。
    if (!processedMessages.Add((source, messageId)))
    {
        Console.WriteLine($"重复，跳过：{source}/{messageId}");
        return;
    }

    // 这里用输出代替实际的患者资料更新。
    Console.WriteLine($"处理：{source}/{messageId}");
}

Receive("HOSP_A/HIS", "MSG-100");
Receive("HOSP_A/HIS", "MSG-100"); // 模拟确认丢失后的重发。
Receive("HOSP_B/HIS", "MSG-100"); // 另一来源，不当成同一条。
```

**输出：**

```text
处理：HOSP_A/HIS/MSG-100
重复，跳过：HOSP_A/HIS/MSG-100
处理：HOSP_B/HIS/MSG-100
```

这里的 `void Receive(...)` 是局部函数，类似你在 Java 中写一个处理方法。第一条首次出现，Add 返回 true，执行处理；第二条键相同，Add 返回 false，提前 return；第三条来源不同，仍然处理。

这只在**同一进程、顺序调用、永不失败的输出模拟**里解释重复识别，没有实现真实患者更新、ACK 或可靠幂等。程序重启后集合会丢失，HashSet 也不是这里的并发控制方案。

而且本例先标记再输出：如果真实业务写入失败，不能将这条消息永远当已处理。生产设计需要持久状态、事务、冲突检查和失败恢复；不是把这段内存集合直接放进接口。

**改一处观察：**把第二次调用改成 MSG-101，会再次处理。这说明消息去重不能单独证明“同一业务意图只产生一次效果”。

## 六、另一个容易懂但很重要的例子：两个 P0001

```text
A 医院：P0001 = 张明
B 医院：P0001 = 李华
```

如果仅用 `P0001` 查询并更新，你可能把李华的信息写到张明记录里。所以应当结合编号所属的标识域理解，例如教学中的“医院＋患者编号”。

也不要只根据姓名合并：可能有两个张明，一个人也可能改名或资料需要更正。实际身份关联由约定的主数据与核查规则管理。

**面试时这比背十几个字段更有价值：**你理解数据传得通，还不够；还必须知道数据属于谁。



### 可选的业务规则模拟｜患者身份：相同编号不一定是同一个人

```csharp
// 键包含医院和患者号；值是展示姓名。
var patients = new Dictionary<(string Hospital, string PatientId), string>();
patients[("HOSP_A", "P0001")] = "张明";
patients[("HOSP_B", "P0001")] = "李华";

Console.WriteLine(patients[("HOSP_A", "P0001")]);
Console.WriteLine(patients[("HOSP_B", "P0001")]);
Console.WriteLine($"患者记录数：{patients.Count}");
```

**输出：**

```text
张明
李华
患者记录数：2
```

`Dictionary` 类似 Java 的 `Map`。`(string Hospital, string PatientId)` 是一个二元组，表示把两个值一起当作键。这里 `(HOSP_A, P0001)` 和 `(HOSP_B, P0001)` 是两个不同的键，所以两位患者不会互相覆盖。

只用 `Dictionary<string, string>` 并把 P0001 当键时，第二次赋值会覆盖第一条。这说明**标识的范围是业务信息的一部分**。真实业务的域可能是签发机构或其他标识体系，不一定等于发送医院；本例用医院便于理解。

**改一处观察：**把第二条记录的 HOSP_B 改成 HOSP_A，看看记录数与第一条查询结果为什么变化。

## 七、第三个例子：旧更新晚到

张明的资料先被更新一次，随后又被更正。网络或重试导致第一次更新的消息最后才到。如果系统简单采用“最后收到的消息覆盖”，旧内容可能把更正后的内容覆盖掉。

这叫乱序问题。开发者要确认哪些系统有权修改哪些字段，以及如何识别新旧。如果有可靠的业务版本，按版本规则处理；没有时，可能需要查询权威来源或核查，不能自造“谁晚到谁更新”的医学规则。

你不需要现在设计完整乱序算法，能举例说明问题并知道要问清更新规则即可。

## 八、面试可以这样说

> 我把 HL7 v2 理解为医疗系统之间的**业务消息标准**。例如医院系统更新患者资料后，通过**消息通知**肿瘤信息系统。开发时不仅要**解析字段**，还要**确认患者编号所属机构**、**消息对应的事件**和**确认响应的含义**。我会特别关注超时重试导致重复、消息乱序，以及同编号跨机构碰撞等问题。这些可以联系我已有的接口、事务和幂等处理经验。

## 九、三道纸面题与答案

**题 1：HIS 超时了，是否一定说明接收方没处理？**

答案：不一定。接收方可能已提交，回复在网络中丢失。

**题 2：消息编号 MSG-100 是不是患者编号？**

答案：不是。它标识消息，P0001 才是本例的患者业务编号，且还要结合所属机构理解。

**题 3：通知“已安排检查”后，能否自动生成“检查已完成”？**

答案：不能。请求、排程与完成属于不同业务事实。
