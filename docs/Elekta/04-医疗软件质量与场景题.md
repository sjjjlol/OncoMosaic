# Elekta｜医疗软件质量与场景题

以下是软件工程面试演练，全部场景为虚构，不代表MOSAIQ实现。产品和标准事实见[官方资料](07-官方资料与事实边界.md)。本岗位明确涉及QMS、验证与客户调查，但未给出系统分类、适用标准版本或内部审批流程。

## 1. 医疗软件和普通业务开发有哪些不同关注点？

可回答：“共通点是正确性、可维护性和稳定交付。医疗软件还需要更明确地理解错误可能影响什么工作流，并让需求、风险、实现、测试和发布证据可追溯。我没有正式医疗软件经验，会先学习团队流程，与质量和领域专家确认验收条件，不自行判断临床行为。”

术语记忆：QMS是组织的质量管理体系；RCA是根因分析；correction处理当前问题，corrective action针对原因防止再发生。CAPA等正式流程如何触发、审批和关闭，要以团队制度为准，不能说每个缺陷都必须走同一套流程。

Verification可用“是否符合规定要求”理解；Validation关注预期用途和用户需要是否得到满足。实际职责分工和证据要求向团队确认，不能简化成“开发单测/测试验收”的固定分工。

## 2. 通用缺陷调查：答题顺序

1. **确认影响与升级：**哪些版本、客户、流程和数据受影响，有没有业务中断或数据不一致；按既定渠道同步支持、质量与领域负责人。
2. **保存证据：**版本、配置、发生时间与时区、操作步骤、关联ID、脱敏日志；保存原始信息再分析。
3. **复现与缩小范围：**建立相同配置的测试环境，比较正常/异常样本，一次改变一个关键变量。
4. **提出可证伪假设：**代码回归、数据差异、接口契约、并发、环境或升级脚本。每个假设对应验证动作。
5. **修复和影响分析：**找触发条件和根因，评估相邻流程、历史数据与兼容性；临时缓解和永久修复分开。
6. **验证与关闭：**原复现用例、相邻边界、回归及发布证据关联到缺陷；由相关角色按流程确认关闭。

“重启好了”是现象消失，不能直接当根因。无法复现时不宣布无缺陷，应说明已排除项、剩余假设、下一次需要的观测信息。

## 3. 场景A：客户升级后部分记录不显示

**两分钟答案：**先确认是显示问题、权限变化、查询过滤、迁移遗漏还是数据实际缺失，不能直接补写生产数据。收集版本组合、升级路径、过滤条件与脱敏样本，在测试环境复现。比较升级前后字段、状态枚举、默认值、权限及时间范围；定位后补回归用例，说明受影响范围和恢复方案，再按流程交付。

**追问与得分点：**

- 数据库中存在不等于用户能看到：关联键、租户/机构范围、状态和权限都要查。
- 新版应用回滚前检查数据库是否向后兼容；破坏性迁移不能靠切回二进制自动恢复。
- 升级测试覆盖旧版本数据、空字段、失败中断、重复执行脚本及备份恢复验证。
- 关联接口迁移故事：可比较的是契约与变更验证，不能声称电商迁移经验等于临床验证经验。

## 4. 场景B：接口超时，用户再次点击，出现重复记录

**答案：**区分请求接收、业务提交、响应返回三个阶段。服务器成功而响应丢失时，客户端看到超时但动作已经完成。为同一业务意图使用稳定请求标识，在事务中以唯一约束/状态机制争取处理权；重复请求返回或查询同一次操作的结果。若请求标识相同但内容不同，应拒绝冲突。外部系统调用仍需要它的幂等/结果查询契约，本地事务不能覆盖远程副作用。

**验证：**并发相同请求、处理后断网、处理中重试、请求ID冲突、服务重启。成功标准是没有额外业务效果，不能只检查接口都返回200。

与退款经历连接：统一锁序解决抢锁冲突，持久状态与幂等解决重复效果，二者不是同一个问题。

## 5. 场景C：两个用户同时修改同一条记录

**答案：**先明确允许的状态转换与冲突处理策略。读取时带版本号，更新时使用ID+旧版本+合法前置状态作为条件，检查影响行数。冲突时让用户看到最新内容并重新判断，不静默覆盖。重要变更保留操作者、时间、对象、变更摘要及原因等审计信息，具体粒度与权限由流程确定。

**追问：**不自动把两次修改合并；不把“最后写入胜出”当作任何业务都合适；多记录约束还要明确事务和隔离级别。

## 6. 场景D：外部系统消息重复、乱序或患者标识不匹配

**答案：**先确认双方协议版本、字段映射、标识命名空间与消息确认语义。传输收到不代表业务处理成功；重复消息需去重，乱序需检查对象版本/状态，不仅看本机时间。标识冲突或关键字段缺失进入待核查状态并告警，不仅凭姓名自动匹配。重放要保留原消息与处理证据，并确认不会重复产生副作用。

**DICOM/HL7/FHIR一句话：**DICOM面向医学影像及相关信息交换；HL7是标准家族，常见v2消息用于系统交互；FHIR以资源模型等机制支持健康信息交换。三者不是可互换的三个HTTP接口，能说清用途比背缩写重要。具体版本与适配范围见官方资料和团队要求。

## 7. 场景E：临时修复很急，测试还没有完成

**答案：**先给出当前影响、可用缓解方案、修复范围和未完成验证项，让相应负责人按紧急变更流程做决定。开发负责提供可复现问题、最小修复、针对性测试与恢复条件；不以“代码只有一行”替代风险评估，也不自行决定临床流程如何继续。

## 8. 一页RCA模板

| 项目 | 应填写内容 |
|---|---|
| 问题与影响 | 观察到的现象、影响对象、时间范围；未知项单列 |
| 环境 | 应用/数据库/依赖版本、配置、升级路径 |
| 复现 | 最小输入、操作顺序、预期与实际 |
| 证据 | 脱敏日志、关联ID、截图、测试结果位置 |
| 根因 | 触发条件、缺陷机制、为什么原测试没覆盖 |
| 措施 | 临时缓解、代码修复、数据处理是否需要单独方案 |
| 验证 | 修复前失败、修复后通过、相邻回归与影响分析 |
| 交付 | 缺陷号、提交、构建、验证记录和后续责任人 |

这是练习模板，不宣称是Elekta官方表单。
