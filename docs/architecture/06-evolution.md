# 06：扩展练习与架构取舍

## 练习一：新增一个分析模型

这是最适合检验当前结构的真实变更。不要先添加一个“模型服务接口”，先写清楚模型能处理什么面板、需要哪些输入、产生什么测量、是否改变统计语义。

1. 在 Domain 中明确模型与阈值组合是否合法，补 `AnalysisScheme` 测试。
2. 若产生新的业务测量，增加相应领域字段和值的合法范围，不要把它藏在无定义的字典里。
3. 检查 Application 的 `IAnalysisEngine` 是否仍能表达输出。仅实现算法不同而业务输出相同，不需要改用例流程。
4. 在 Infrastructure 和 Python 协议中实现适配，扩充 manifest 校验。未知字段或文件不应直接变成可信结果。
5. 如果持久化结构变化，生成迁移并审查旧记录的默认含义。
6. 更新 `AnalysisRepository.ClaimNext` 支持的模型列表；查询已使用领域模型常量和参数化 SQL；模型增多时应进一步抽出统一模型目录。
7. 补 Python 契约、.NET 领域、发布事务和端到端导出测试。
8. 最后才加前端选择项及展示。确认旧模型、旧复核与旧导出仍能读取。

这个顺序体现从语义到实现。若只是新增模型名，却没有讨论输出单位或质控规则，工程分层无法保护结果含义。

## 练习二：增加可信的复核身份

本轮没有认证。未来增加时，Api 负责验证凭据并从服务端身份上下文取得用户标识；应用用例接收可信 actor；Domain 只表达“谁在何时作了何种修订”等必要事实；Infrastructure 保存审计字段。

不能让浏览器传一个 `userName` 就当成可信操作者。还要决定项目访问权限、复核权限、历史账号删除后如何显示、审计能否被修改。这些是业务与安全决策，不是加一个 JWT 中间件就结束。

## 练习三：扩到两个 worker

先写失败场景：worker A 领取后失联，B 接管；A 又恢复并返回旧结果。只靠 Status 不能区分谁有权发布。

需要任务租约、到期时间、心跳、执行令牌与 fencing 检查；启动时不能无差别回收 Running；文件发布也应区分尝试或验证同一结果身份。单机 Python 锁和共享目录不足以代表跨节点安全。之后才评估数据库队列是否仍合适，或是否需要消息队列、对象存储和独立 worker 宿主。

## 哪些模式暂时没有采用

**微服务**：当前部署和团队规模不需要独立发布边界；拆服务会增加网络、版本与运维成本。

**通用仓储**：任意 CRUD 无法表达领取、原子发布和复核锁语义；会迫使调用方重新理解事务细节。

**MediatR / 每用例一套 Handler 接口**：当前应用类已足够明确，没有统一复杂管道需求。未来有大量横切行为再考虑。

**完整 CQRS 或事件溯源**：读写代码已有职责分离，但不需要独立读库和全量事件重放。复核的追加版本只解决当前历史追溯问题，不等于整个系统使用事件溯源。

**为算法强加类层次**：确定性计算保持纯函数更容易推理与测试；只有可替换外部引擎才需要端口。

## 本轮仍可继续改善的地方

当前 JSON 字段、部分匿名统计结构、仓储接口粒度及文件对账都有继续演进空间。特别是大数据量下，全量加载细胞和内存 ZIP 会增加内存压力，需结合容量目标决定分页、流式导出或异步导出任务。没有测量数据前，不应声称这些实现适合任意规模。

新需求评审时依次问：影响哪个业务事实？属于哪条用例？涉及哪些外部资源？要求什么一致性？用什么失败测试证明？最后再决定加哪些类。这个顺序比从设计模式名单中挑选更可靠。
