# 01：先确定业务与失败语义，再选择架构

## 1. 为什么不能从“建四个项目”开始

分层只能分配已经理解的职责。若没有明确业务规则，把一个巨大的 Program.cs 拆成四个同样混乱的目录，仍然无法判断事务该放在哪里、数据能不能修改、重试会不会破坏结果。

本项目的主要使用链路是：建立项目 → 导入图像与伴随资料 → 圈选 ROI → 提交分析方案 → 等待执行 → 查看原始测量与质控 → 追加人工复核 → 对比区域 → 导出固定版本结果。先沿这条链列出输入、输出和必须保持的事实。

| 用例 | 输入 | 成功结果 | 主要拒绝条件 |
|---|---|---|---|
| 导入图像 | 图像、assay、名称 | 已校验文件及图像元数据 | 超限、校准不匹配、元数据不合法 |
| 创建 ROI | 原图坐标、名称、标签 | 持久化区域 | 越界、非正尺寸、非法标签 |
| 提交分析 | 图像、ROI、模型、阈值 | Queued 任务 | 图像不匹配、阈值不合法、Ki-67 方案不完整 |
| 执行分析 | 已持久化任务 | 原始测量、产物索引、成功状态 | 服务不可用、超时、结果契约不符合 |
| 追加复核 | 对象、维度、判定、基础版本 | 新修订版本 | 非成功任务、对象不属于任务、版本过期、质控不允许 |
| 读取或导出 | 任务和复核版本 | 可追溯快照 | 任务未成功、版本不存在、产物缺失 |

## 2. 从流程中找不变量

“不变量”是在所有入口和执行顺序下都必须成立的业务事实。本轮最关键的是：

1. ROI 坐标属于原始图像，矩形必须完整落在图像范围内。
2. 分析任务的方案在创建后固定；重试仍使用同一个任务身份。
3. 一次真正开始执行才消耗一次尝试，排队不消耗次数。
4. 成功结果不可通过重试或迟到响应替换，尤其不能替换已被复核引用的细胞 ID。
5. 复核是对解释的修订，不是对原始测量的篡改。
6. 未测量或质控不通过的 Ki-67 信号，不能靠人工复核变成有效信号。
7. 两个区域的“最新版本”比较必须在同一数据库快照内解析。

这些规则决定了 `AnalysisRun` 的行为方法、`ReviewPolicy` 的校验以及事务边界。它们比“是否使用 Repository 模式”更早确定。

## 3. 区分业务事实和工程策略

“成功结果不可改写”是业务事实。“最多执行三次”是当前工程策略；将来可以调整，但必须同时修改恢复、重试、测试和运维说明。“运行一个 worker”是部署约束；不属于领域术语，却直接决定启动恢复是否安全。

这里没有把所有实体都设计成拥有复杂行为的聚合。Project 与 Artifact 主要承载稳定事实，使用初始化属性即可；AnalysisRun 存在明确生命周期，因此封装状态转换。核对象保留数据模型形态，纯量化函数计算结果。类的复杂度应来自业务复杂度。

## 4. 给非功能需求一个具体含义

可维护性：HTTP handler 不需要知道 MySQL 行锁或 EF 实体跟踪；领域规则测试不需要启动 Docker。

可恢复性：进程中断留下 Running 记录时，下次启动能够在预算内重新排队；第三次中断变为 Failed，避免无限重启循环。

可追溯性：保存图像及 assay 哈希、模型与算法版本、阈值、复核版本和产物哈希；错误响应携带 traceId，worker 错误日志带任务标识。

可交付性：解决方案可统一构建，包版本有 lock 文件，容器构建使用 locked restore，数据库升级有显式命令，测试覆盖真实 MySQL 事务。

这些是工程能力，不是临床有效性或安全上线证明。认证、授权、容量目标、备份恢复演练、依赖漏洞处置仍需在真实部署项目中补齐。

## 5. 在本轮开始前就确定的取舍

以长期维护为主、多人协作为辅；使用四层单体学习 .NET 架构；兼容性不是硬约束，但不随意改变科研语义；单实例可靠性优先；本轮不建设账号体系；一次性完成实现后交付详细文档。由这些目标推导架构，避免为了展示技术而引入额外设施。
