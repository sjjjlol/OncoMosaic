# 03：按业务切片推进开发

下面的顺序适用于新项目，也解释本轮为什么不能只按“先写完所有实体，再写完所有服务”推进。一个切片应从业务规则贯通到可运行入口和验证。

## 第一步：建立可编译的工程骨架

创建四个 SDK 项目和一个测试项目，使用 `OncoMosaic.slnx` 统一组织。Domain 不引用其他项目；Application 只引用 Domain；Infrastructure 引用 Application；Api 引用 Infrastructure，在组合根装配依赖。统一目标框架、nullable、隐式 using 与编译警告策略放在 `Directory.Build.props`，减少项目之间的配置漂移。

不要先引入通用基础实体、万能仓储、ServiceBase、事件总线或 MediatR。只有业务流程需要它们时，再评估减少了什么重复、增加了什么认知成本。

## 第二步：实现“提交分析”这个最小切片

先写规则：ROI 必须属于指定图像；阈值必须有限且在 0–1 内；Ki-67 面板必须使用对应模型与阈值。这些判断不需要数据库，所以放在 `AnalysisScheme.Create` 并写纯测试。

接着写应用流程：`AnalysisService.Create` 读取 ROI 和图像，调用规则创建任务，保存任务，返回任务。应用层负责“需要哪些事实、按什么顺序完成用例”，不是搬运 HTTP handler。

然后定义持久化端口并实现 EF 仓储。最后才加 HTTP 端点：绑定 RunInput，调用应用流程，返回 202 与状态查询地址。202 表示已接受排队，并不意味着分析已成功。

## 第三步：把执行器和宿主分开

`AnalysisProcessor.ProcessNext` 处理至多一个任务：领取 → 读取输入 → 调用分析引擎 → 原子发布。调用方得到是否有任务可做。它不负责睡眠、无限循环或创建依赖作用域，因此容易单独驱动和测试。

`AnalysisWorker` 才是 .NET BackgroundService：管理 scope、轮询间隔、取消和日志。宿主取消时不把任务伪装成普通分析失败，数据库中的 Running 状态保留给恢复流程。其他错误先尝试保存失败状态，再由宿主记录原始异常；若保存失败，下轮恢复会重新处理残留 Running。

基础设施的 `AnalysisEngine` 调用 Python 并使用 `ManifestValidator` 检查坐标、尺寸、核掩膜、面积、质控、定量图和文件哈希。不能因为 HTTP 返回 200 就把外部响应当成可信业务结果。

## 第四步：加入复核，重新审视事务边界

复核并不是简单插入 ReviewChange。它需要读取任务状态、对象归属和当前修订版本，检查规则，然后分配下一版本。若检查与保存不是同一个序列化范围，两次请求可能同时看到旧版本。

因此 `ReviewService.Add` 在 `WithLockedRun` 内完成整个过程。`ReviewPolicy.Validate` 保持纯规则，Repository 提供事务和锁。版本检查应在锁内发生，不能只在 HTTP 接口开始时检查一次。

## 第五步：实现读取与导出

先把原始测量和修订重建为 `ResultSnapshot`：选择版本，将该版本内的修订按顺序应用到独立的有效判定字典，然后运行纯统计。不要覆盖原始 Cell 数据来方便查询。

导出器接收已经解析好的快照，再完成 CSV、PNG、JSON 和 ZIP 写入。PNG 绘制与文件访问属于 Infrastructure；不需要 I/O 的比较 CSV/ZIP 序列化位于 Application。两者都不决定什么版本有权被读取。

## 第六步：再处理启动和部署

数据库迁移、演示数据导入、后台任务启动是不同动作。普通运行默认不迁移、不导入；Compose 演示配置显式开启它们。`--migrate` 只执行迁移后退出，不启动后台服务。这样生产发布流程未来可以用独立迁移任务和权限较小的运行账号，而不必修改业务代码。

## 第七步：每个切片都留下验证证据

规则用纯测试，事务用真实 MySQL，推理用 Python 契约测试，页面和下载用浏览器端到端测试。不能把“接口编译成功”当成整条流程成功。尤其不能用 EF InMemory 来证明 MySQL 行锁有效。

本轮先保留原有算法和端到端基线，再增加生命周期、复核和事务测试。这比给每个一行转发方法写一个 mock 测试更能保护重构。
